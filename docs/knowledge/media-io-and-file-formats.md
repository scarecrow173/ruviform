# メディア I/O・ファイル形式・serde 境界

この文書は、後に削除された過去の実装記録から抽出した、メディア I/O・ファイル形式・serde 境界に関する再利用可能な設計・実装知見をまとめたものである。対象は ruviform ワークスペースの I/O 系クレート群であり、各知見には出典となった Issue 番号を付記する。実測値や観測された挙動と解釈は区別して記し、未確定・保留事項は末尾に集約する。

## メディア I/O の抽象境界

`ruviform-media-io` は demux/mux・decode/encode を分離した 4 系統 trait（`Demuxer`/`Muxer`/`Decoder`/`Encoder`）を単一クレートに集約した (Issue #20)。外部クレート依存ゼロ・`unsafe` 不使用・domain 3 クレートへの `path` 依存のみという構成で、domain 型の再エクスポートと外部型・feature 名の露出を禁じ、全公開 API に `**RT contract:** non-RT only` ラベルと `#[non_exhaustive]` を適用する契約とした。

`Packet` は所有バイト列の値型、`AudioFrame` は `AudioBuffer`+`MediaTime` PTS+`Option<MediaDuration>` を束ねる名前付き型で `VideoFrame` と形状対称とした。タプル返却は採用しなかった。EOS は `Err` ではなく `Option`/終端表現で表し、能力交渉は照会 API と `Error` 非対応分類の両機構を備える (Issue #20)。

Decoder の出力は `Frame` enum（`Audio`/`Video`・`#[non_exhaustive]`）を採用した。ストリーム種別ごとの型付き受け口案は 4 trait 分離構造と不整合になるため棄却し、`Decoder`/`Encoder` の対称性を確保した。spec 明示を超えて `drain()` を追加したのは、AAC encoder delay や B-frame 並替のような遅延 codec を境界が駆動完了するために必須と判断したためである。`Packet` の pts/dts/duration は全て `Option` とし、コンテナが全 unit に時刻を持つとは限らないことを契約化した (Issue #20)。

`MediaSource` は `Read+Seek+Send` の blanket impl とした。`byte_len` デフォルトメソッドは blanket impl との coherence 衝突で手動 impl が構造的に不可能（dead 拡張点）と判明したため削除し、実際の長さは `SourceAdapter` 構築時に `stream_position`→`seek(End)`→復元の手動 probe を 1 回実行して `{seekable, len}` をキャッシュする方式にした。`Seek::stream_len` は Rust 1.87 安定化で MSRV 1.85 を超過するためである。真に非シーク可能なソースは `Unseekable`→`Unsupported` に正規化する (Issue #20)。

`Capabilities` は 4 bool が `clippy::struct_excessive_bools` に抵触したため `Features` u32 bitset へ再設計した。`CodecId` は `#[non_exhaustive]` の Ruviform レジストリ+`Other` で未知 codec の列挙を可能にした。`Packet`/`AudioFrame` は I/O・デコードスレッド→有界キューの境界をまたぐため `Send` を契約化し、`fn assert_send<T: Send>()` 相当のコンパイル時断言を単体テストで固定した (Issue #20)。

`symphonia` は default features のみ（`all` 等の特許対象 codec feature は非有効化）・MPL-2.0 のファイル単位コピーレフト調査を PR に記録・バージョンを Cargo.toml/lock で pin し、API 接触面を io-symphonia 内部のラップ層に隔離して 0.5→0.6 の API churn 波及を遮断した。in-memory `MediaSource` が既存実装に適合しない場合は、バイト列 backed の `MediaSource` をバックエンド内部に自前実装する（公開露出なし）方針を採った (Issue #20)。

能力交渉の実例として、symphonia backend は demux+decode のみ提供し `Muxer`/`Encoder` は照会 `capabilities()` と要求 `make_muxer()`/`make_encoder()` の両機構で `ErrorKind::Unsupported` を返す。`capabilities()` は under-claim（DEMUX|DECODE + registry 既知名 codec のみ広告し、decode 可能でも `CodecId` 未登録の ADPCM 等は主張しない）とし、`Packet` フラグは backend が keyframe/corruption 属性を提供しないため捏造せず `NONE` とした。seek は `SeekTo::Time{track_id:None}`+`SeekMode::Accurate` の request-only で実着地点は返さない (Issue #20)。

`symphonia` 採用に伴い上流起因の制限を crate doc に明記した。data len=0xFFFFFFFF の末尾欠損+`UnexpectedEos` 誤分類、block_align 非倍数の残端末の静かな欠損、Ogg gapless trim（trim_start/trim_end）不運搬、チェーン Ogg の `ResetRequired`→`InvalidData` 打ち切り（streams() スナップショットモデルとの構造的衝突）の 4 件である (Issue #20)。

`Muxer`/`Encoder` は実装者ゼロの未検証契約として doc に明記し、ADR Verification 第 3 項（複数バックエンド間の透過切替）も第一バックエンドのみでは検証不能として Deferred に据え置いた。過剰汎用化を避け PoC が通る最小契約で確定する方針であり、ロールバックは依存方向（io-symphonia→media-io）に従い io-symphonia 側を先に戻す必要があると明記された (Issue #20)。

`cargo test --workspace rt_` の部分文字列フィルタが `assert_`/`start_`/`convert_` 等の非 RT テストを誤選択するため、`rt_` を含まない命名規約を実装バインドとし `mise run test-rt` のレーン監査を完了条件に含めた。この部分文字列フィルタの精度限界は Issue #18 と共通の既知制約である (Issue #20)。

## オーディオデバイス境界

`ruviform-audio-core` は planar f32 正準の音声データモデルを持つ。sealed `Sample` trait（`f32`/`f64` のみ・`const BYTES`・f32 が RT 正準）、`SampleRate`（`TimeBase(1/rate)` 内部保持・`rate > 0` を構築時に構造的に保証）、`SampleIndex`、`SpeakerMask`（全 `const fn`）、`ChannelLayout`（Mono〜7.1+`Custom`）、`#[non_exhaustive]` `SampleFormat`、planar `AudioBuffer` と view 型、`from_interleaved`/`copy_to_interleaved`/`copy_from_interleaved` 境界変換（確保系は non-RT、成長 API なし）を備える。全公開 API に `**RT contract:**` ラベルを付与した（89 箇所を確認。未ラベルはフラグ型の関連定数 8 件のみで型レベルラベルでカバーする粒度判断）(Issue #18, Issue #20)。

`SampleRate` は brief の `u32` スケッチから `TimeBase(1/rate)` 内部保持へ変更し、`rate > 0` を構築時に構造的に保証した（公開影響は `PartialOrd`/`Ord` 追加のみ）。`AudioBuffer::new` は `channels * frames` の usize overflow と `isize::MAX` バイト超過で panic し、形状エラーは `Result` コンストラクタ側へ寄せる coordinator ruling に従い `# Panics` に両パスを明記した。`ChannelLayout::Custom` 空マスク・`frames == 0` は panic せず 0 チャンネル/0 長に縮退する (Issue #18)。

デバイス境界ポートは `pub mod device` に 3 object-safe trait（`DeviceEnumerator`・`Device: Send`・`OutputStream: Send`）、値型 7 種、コールバック型 2 種、`#[non_exhaustive]` `DeviceError`+`DeviceResult`、`DEVICE_CLOCK_TIMEBASE`（ナノ秒 `TimeBase`）を定義した。crate root への flat re-export は意図的に行わない。`DEVICE_CLOCK_TIMEBASE` は `TimeBase::new` が `const fn -> Result` のため `match` による const 評価で `pub const` を実現した（`unreachable!` は書式マクロ展開が非 const のため literal `panic!` を使用）。`AudioBufferViewMut::try_new` は借用のみ・非確保・RT-suitable な形で追加した。モック backend（StubEnumerator/StubDevice/StubStream）による契約テストで「非 cpal 実装でもポートを実装できる」を audio-core 側で先行機械検証した (Issue #23)。

`ruviform-audio-device` の cpal adapter は cpal 0.18 を直接依存とし（optional+feature 方式は却下）、`host.rs`/`device.rs`/`stream.rs`/`convert.rs`/`error.rs` に分離した。公開面は `Host`/`HostId`（opaque）/`default_host()`/`available_host_ids()`/`host(id)` の 5 項目のみで、cpal 型・エラー・feature 名を一切露出しない（`cargo doc` 生成物への grep で機械確認）。エラー正規化は `map_error(e, ctx)` 1 関数集約で `ErrorCtx::{Control,ErrorCallback}` を区別し、`DataCallbackState`（callback+scratch+clock profile）は data クロージャへ `move` 所有で `Arc`/`Mutex` 非共有、scratch は open 時に `min(effective_max, FRAMES_CAPACITY_HARD_CAP=16_384) * channels` で 1 回確保した。`negotiate` は F32 優先・`Fixed` は一致候補のいずれかの報告 Range が受容すれば可・報告 bound は候補単位で `min<=max`・非零上限を検証する untrusted-data 防御を行う。feature 名は `realtime`/`pipewire-backend` の意図命名で固有名詞を避けた (Issue #23)。

cpal の既知リスクとして、PipeWire の `!Send` リスク・`BufferSize::Fixed` が backend に尊重されない可能性（chunk 分割経路が構造的に吸収）・WASAPI xrun 未報告・Linux の `libasound2-dev` 必須/`libpipewire-0.3-dev` 任意・ASIO `build.rs` の SDK 自動ダウンロードによる再現性低下（ASIO feature は既定無効で回避）を列挙し、実機観測対象として実験ログへ記録する運用を定めた (Issue #23)。

実機検証は `real-device` cargo feature + `#![cfg(feature)]` + `#[ignore]` + 専用 mise task で既定 `cargo test`/`lint` から分離する。失敗ポリシーは「device 非存在は環境要因として loud SKIP（print+pass）、device が存在する以上の全契約違反（open 失敗・callback 0・timestamp 逆行・non-finite sample 等）は hard fail」である (Issue #114, Issue #251)。

WASAPI 実機検証（Issue #251 Stage W、Audient iD4・44.1 kHz F32 Stereo）で callback timestamp の provenance 欠陥を発見した。cpal 準拠の `IAudioClock::GetPosition` qpc は「position counter が最後に更新された瞬間」の snapshot であり、stream 最初の packet では clock 未開始で `0` を返し callback instant が epoch 0 に落ち（観測 delta = −319936 秒）、以後も packet record instant より最大 ~1ms 遅れ `capture > callback` が 193 中 47 packet で発生した（実測値）。port 契約は callback を「host-observed delivery instant」と規定するため、packet 処理時点の `QueryPerformanceCounter` 直読み（`perf_counter_instant`）へ修正した。修正後 order violations=0・実効 latency ~10.04–10.12 ms（1 period pipeline delay）に収束した（実測値）。`IAudioClock` service 取得・`clock_callback_instant` を削除し `RunContext` に `qpc_frequency` を追加した (Issue #251)。

`clock_profile(host_name)` は cpal 0.18.2 source 監査に基づき、共有 monotonic clock を持つ `WASAPI`(QPC)/`CoreAudio`(`mach_absolute_time`)/`PipeWire`(graph clock) のみ `ClockDomainId::MONOTONIC`、per-device clock の `ALSA` と未監査 host は `UNKNOWN` を報告する（`same_clock_domain` は `UNKNOWN==UNKNOWN` を same-clock と見なさない規則と整合）。`input_latency()`/`output_latency()` は cpal が portable latency query を公開しないため `Ok(None)` の正直応答（`Ok(0)` 捏造も backend 別推定値も出さない）。`frame_position` は cpal 非公開のため常に `None`（callback 回数の合成 counter は真の discontinuity を隠すため不採用）。`StreamInstant::ZERO` は backend の "未報告" sentinel として `capture=None` に写像し、overflow も callback 値代替せず `None` とする。非 F32 config は `UnsupportedConfig` で拒否し黙って変換しない (Issue #251)。

output latency の delta=0 は違反ではなく正直な floor である。cpal 0.18.2 の WASAPI `output_timestamp` は `playback = callback + (buffered + stream_latency)` で、`buffered` は written−consumed の飽和差分（stream 開始直後・underrun で 0 に張り付き）かつ `monotonic_output_callback` が playback を非減少に clamp する。本 driver は `GetStreamLatency` 相当が ~0 を返すため buffered 飽和時に `playback == callback`（delta=0）へ正当に退化する。初回実装の「`playback ≤ callback` は ordering violation で hard-fail」案は実機で 102 sample 中 3 件の delta=0 を観測して棄却し、input 側の `capture > callback` assert（物理的にあり得ない順序）とは性質が異なり同一 policy を機械適用しない判断を記録した。latency 値は assert せず記録する（backend estimate であり物理 DAC instant の保証値ではない）(Issue #251)。

## デコード prefetch パイプライン

seek は ring purge ではなく ordered boundary とした。SPSC topology は公開済み item を retract できず、consumer 側の「boundary まで drop」は RT thread への第 2 制御経路を要するため棄却した。seek 前に queue 済みの block は旧 generation として順序通り再生され `Boundary` item が generation を反転し、hard truncation が必要な caller は pipeline を rebuild する契約である。`End` は generation 毎に 1 回だけ emit され consumer は `ended` を latch する（EOF は event でなく state）。fault span は zero-fill+計数で silent にしない。EOF/backpressure で parked block は保持され、close audit が producer/consumer 両側で `block_count` を reclaim する (Issue #197)。

data ring 容量は `block_count + MARKER_SLACK` とし、Boundary/Fault/End marker が満杯 ring で停滞しないようにした。symphonia の `make_decoder` は `Self` を返すため trait 境界で `Ok(Box::new(self.make_decoder(id)?))` と wrap し、`Native` モードは `make_native_decoder` を wrap する。WAV の symphonia seek は `SeekMode::Accurate`+pts ticks=sample index で frame-accurate だが codec backend は早着し得るため `SourceReader::seek_source_frame` で decode-discard 前進し、着地>要求は `SeekReceipt` で報告する (Issue #197)。

`DecodeMode::{Canonical, Native}` を追加し、canonical（f32 planar playback）と native（f64/native-scale observation）を明示的に分離した。f32 playback path が high-fidelity observation を強制しないための設計である。boundary 追加は厳密に additive（defaulted `Demuxer::seekable() -> Fact<()>`・defaulted `make_decoder(id, mode)`・新 enum・1 re-export、既存 signature 変更なし）とした。symphonia は構築時 source-seekability probe で `Known(())`/`Unsupported` を報告し、AVI は `seek()` の error と一致する `Unsupported` を構築時に宣言する（`movi` index reader が将来 upgrade する余地）(Issue #197)。

Issue #233 では 4 件の additive 改善を載せた: `expected_first`/`pump()` の doc-only 契約改訂、consumer 側 `discard_pending` ドレイン補助+producer 側 `seek_discard_pending` pending purge、融合 `reopen_at`。破壊的変更を避けるため変更は private `PrefetchCmd` と新規 public `DiscardReport` に限定し、`PrefetchItem`/telemetry/公開 signature は不変とした (Issue #233)。

`discard_pending` は consumer 側で in-flight `current` block を free ring に返し、ring item を `step()` と同一規則で処理して最初の `Boundary` または ring-empty で停止する有界 drain（alloc/lock/blocking なし）である。ring backlog は consumer ownership、producer `pending` queue のみが producer 側 purge 対象という責務分離である。`reopen_at` は成功時に reopen 後 `seek_source_frame` → `Boundary{first_frame: reader.position().0}`（実 landed 位置を正直に報告）を emit し、post-reopen seek 失敗は `Fault{Unseekable}`+reopened 位置の `Boundary`、reopen 失敗は既存の `Fault + stream_ended`（Boundary なし）を維持する (Issue #233)。

却下した代替案は、shared requested-generation cell（generation model 変更が必要）、`PrefetchItem::Discard` marker variant（public enum 互換性リスク）、pending-purge-only（ring 内 item は consumer ownership のため不完全）の 3 件である。documented residual として、`discard_pending` は drain 完了後・Boundary 到着前に届いた item を捨てられない（boundary-driven model の帰結であり #197 contract を変えない限り除去不能）。厳密な再 anchor は「`seek_discard_pending` を pump した後に `discard_pending` を呼ぶ」使い方を rustdoc に明記した。`reopen_at` は replacement source の seekable を pre-check しない（reopen 後でないと不明）(Issue #233)。

Issue #244 では残存 wart 4 件を ADR Option A で無条件修正した（opt-in ではない意図的な観測挙動変更で、API signature/型/variant は不変・source-compatible）。(1) failed seek/reopen の emission を `Fault`→`Boundary` から `Boundary`→`Fault` へ反転し consumer が generation adopt 後に fault を `fault_events`/per-kind `faults` に計上する（旧来は `stale_drops` 行き）。(2) reopen の `open`/`reopen` 失敗に `Boundary{gen,0}` を追加し dead generation を `Boundary`→`Fault`→`End` で終端する（dead-generation anchor は要求 target でなく frame 0 — stream が一度も開始していない honest anchor で、要求値は `Fault.first_frame` に残る）。(3) `end_emitted` を `try_push` 前の synthesis 時点で latch し ring-full requeue での duplicate `End` を抑止する。(4) `SeededSource` fixture（`Arc<AtomicBool>` gate で construction 後の最初の `Read`/`Seek` を原子的に失敗化、construction 時の symphonia probe は unarmed で通過し seekable `Fact::known` を確保）で fault 経路を deterministic に seeded した (Issue #244)。

Issue #249 では `PumpOutcome::Ended` の semantics を「`End` marker がその call で ring に載った」に整合させた。既存 rustdoc が既に "the stream's `End` marker was emitted" を約束しており contract の自己矛盾を最小にする修正と判断し、文書修正のみの選択肢は manual driver に trap を残すため棄却した。`emit_end` helper に commit-once synthesis+push/requeue を集約し、EOF 検出 pump が `End` を同一 step で emit する（ring full なら `pending` commit 済み `Backpressured`）。fault arm は `Fault` を `pending` back に積むため eager 化すると ring 上で `End` が `Fault` を追い越し `Fault`→`End` ordering が壊れる — step 2 lazy が唯一正しい経路として維持した (Issue #249)。

## ファイル出力と staged publish

`ruviform-media-io` の旧 `StagedOutput` は `ruviform-io-file` の型状態 API（`StagedFile`/`SealedFile`/`ReadbackFile`・`PublishOptions`・`PublishReceipt`/`PublishFailure`/`RecoveryHandle`/`CleanupReceipt`）へ置き換えられ、互換層なしで完全削除された (Issue #305)。`StagedFile` は `Write+Seek+Send`、`seal()` で `SealedFile` へ遷移し `SealedFile` は `Write`/`Seek` を実装しない（compile-fail doctest で pin）。

`ReadbackFile` は同一 staged object の `Read+Seek` で position 0 開始の非 File borrow とする。匿名 path の再 open は TOCTOU を招くため契約上の安全な実装と偽装せず、adapter が安全な read surface を提供できなければ `Unsupported` を返す。trait object の multi-bound upcast が不安定なため private `ReadSeek` supertrait 経由で内部 object を運び、公開 accessor は opaque `impl Read+Seek` を返して File 型・clone 可能 handle を露出しない (Issue #295)。

publish の効果分類は `Result` ではなく `ApplyOutcome`（Applied/NotApplied/Unknown）+`TempDisposition` を返す契約とし、ambiguous な OS エラーが `NotPublished` に正規化されない構造にした。`PublishEffect` は `NotPublished`/`Published`/`Indeterminate` の三分類で、`Ok(PublishReceipt)` は要求 durability の全達成時のみ返す（dir sync 失敗は `Published`+`Err`・evidence=`FileSynced` で成功を偽装しない）。Indeterminate/失敗時の temp は自動削除せず `RecoveryHandle` が所有権を持ち、Drop は削除しない設計（明示 `cleanup()` のみ削除）。`RecoveryInfo` は診断 snapshot に限定し identity 証明・lock・CAS token には使わないと rustdoc で明記し、handle 移譲で二重削除・置換済み temp identity の誤削除を構造的に防止する (Issue #295)。

Drop を実装する型からフィールドを move できない Rust の制約に対し、`StageOwner` が `ops: Option<Box<dyn PlatformFileOps>>`+`RecoveryInfo`+`cleanup_on_drop` を持ち `Option::take` で adapter を outcome の `RecoveryHandle` へ移譲する構成を採用した。`StagedFile`/`SealedFile` 自体に Drop は実装せず `StageOwner` に集約し、review-protocol で検出した P1（所有権喪失）を修正した。未 publish の temp のみ best-effort 掃除し、Indeterminate 残存物には関与しない (Issue #295)。

atomic CreateNew の OS 別 primitive は、Linux/Android は libc::renameat2 wrapper が全 unix target で宣言されないため std と同じく `syscall(SYS_renameat2, RENAME_NOREPLACE)` の raw syscall を採用（unsafe は `#[expect(unsafe_code)]` で局所化）。`ENOSYS`→`link`+`unlink`、`EINVAL`→fallback 後に非 EEXIST 失敗なら元 errno を報告する std の再検査規則に揃えた。Apple は `renamex_np(RENAME_EXCL)`、その他 unix は `link`+`unlink`、Windows は `MoveFileExW(temp,dest,0)` で `exists()`+`rename` 組合せは不使用。Replace は両 OS で `fs::rename` (Issue #296)。

エラー分類は確定的失敗（EEXIST/EACCES/ENOENT/EISDIR/EOPNOTSUPP 等）=NotApplied+Retained、ambiguous（EIO/ETIMEDOUT/ESTALE/ENOLINK/ネットワーク・デバイス系）=Unknown+Unknown（→`PublishEffect::Indeterminate`、`TempState::Unknown`）に正規化する。`link` の `EPERM`/`EOPNOTSUPP`/`ENOSYS`/`ENOTSUP` のみ capability failure として `Unsupported` に正規化し、権限失敗を根拠なく `Unsupported` にしない。Windows の `ERROR_ACCESS_DENIED` のみ宛先 `symlink_metadata` を 1 回診断 probe するが、probe は分類専用で atomic 機構ではない (Issue #296)。

dir sync は unix で親 dir `fsync`、Windows で `FILE_FLAG_BACKUP_SEMANTICS`+read-write open+`FlushFileBuffers`。FS が dir sync を提供できない場合は `DirectorySync` phase の失敗として正直に報告し `Published`+`FileSynced` evidence を返す（false Ok にしない）。temp は sibling `<name>.rvf-tmp-<token>` を `create_new` で排他生成（collision retry 64 回）し、path は create 時に `std::path::absolute` で保持して cwd 変更による temp/宛先の dir 分裂を防ぐ。`BestEffort` visibility でも atomic primitive は常に使用し弱い fallback は作らない (Issue #296)。

`unsafe` は `#[expect(unsafe_code, reason)]`+SAFETY コメントで FFI 呼出しのみに局所化し、unsafe は FFI 呼出し 2 箇所のみに限定した。cfg(unix)/cfg(windows) 毎に正確に expect を置き、`lint -D warnings` ゲートで未使用 expect は fail するため target 毎の正確な配置が必要である (Issue #296)。

consumer 移行（Issue #305）では `RenderError::Publish { source: PublishFailure }` に変更して `PublishFailure` 全体（effect・phase・durability 証跡・RecoveryInfo・RecoveryHandle）を保持し、非 Indeterminate の publish 失敗は `RecoveryHandle::cleanup` を best-effort 実行、Published/Indeterminate は handle を failure 内に保持したまま `RenderError::Publish` とする（決して自動削除しない）。verify フックは `FnOnce(&mut SealedFile,&OutputFacts)` で sealed object の `open_readback` 経由でのみ検証でき publish を bypass できない境界とし、出力 tail の順序は finalize 成功→muxer drop→seal→readback verify（任意）→publish とした。preflight の早期 `DestinationExists` はレンダリング省略に過ぎず、原子性の根拠はあくまで publish 側の atomic no-replace primitive である。裸 closure の `as _` は trait object を `'static` に潰すため `for<'a>` 署名を持つ named fn helper 経由で HRTB 一般化を保証した (Issue #305)。

post-seal temp 境界は「publish は seal 後の temp 内容を再検証しない」現行契約を維持すると確定した（Issue #721）。consumer 全利用（audio-lens `al-job`/`al-media`、synvelis `synvelis-library`/`synvelis-player`）が同一信頼境界内の連続 pipeline であり post-seal 改竄を脅威モデルに含めない。強化案 3 件（seal 時権限強化・publish 時再検証・temp 配置分離）はいずれも同一信頼境界内では実効なし+OS 別複雑さ/TOCTOU 残存のため却下し Deferred に再検討トリガー付きで記録した。seal 時 read-only 化・owner-only ACL は同一信頼境界内の攻撃者（同一ユーザ）が権限変更・削除再作成可能で実効的境界を生まない、publish 直前の内容再検証は publish 毎に temp 全体の追加 read で hot path コスト+再検証〜rename 間の TOCTOU 残存、temp 配置分離は staged publish の前提（temp と宛先が同一 filesystem 上で atomic rename 成立）を崩す、という評価である (Issue #721)。

## 構造化フォーマットと serde 境界

Serde 境界の横断契約は、許可型/非公開型/`source()` のみ診断/自作 Serializer・DOM・Registry なしを固定した。Format/Version 契約は schema/version/canonical bytes は Consumer 所有・Format A→DOM→B 非提供とし、Resource Budget 3 層・Error 契約・Feature/Backend 確定値・証拠項目対応を IO-02 横断設計正本として定めた (Issue #284)。

`ruviform-io-structured` は feature matrix default=[]・json/yaml/toml/file で、json/yaml/toml 各 module が共通形 `from_reader<T>`/`to_writer<T>` を提供する。公開 API に出る外部型は `serde::{Serialize,DeserializeOwned}` のみで、backend（serde_json/serde-saphyr/toml）の型・エラー・feature 名は露出せず診断は `Error::source()` の dyn Error 経由のみ。`DocumentError` は kind+format+position+limit+type-erased source を持ち、Display は backend レンダリングや入力 snippet を一切埋め込まない (Issue #297)。

「公開 signature に backend 型名がない」の機械監査は、公開型の `std::any::type_name` canonical path が `ruviform_io_structured::` 名前空間に留まり backend crate 名を含まないことを検査する方法で実現した。ただし関数 signature 引数・戻り値の backend 型混入は網羅しないため per-format test-spec の目視/grep 規則との併用が前提である。`serde_json` の深度 probe は `deserialize_ignored_any` では不十分（深度 accounting を通らず 256 段 nesting を受理した）ため、実再帰を強制する `serde_json::Value` へ deserialize 先を変更した (Issue #284)。

`BoundedRead` は budget 消尽後に 1 byte probe で真の EOF かを判別し、「丁度 budget の文書は受理・1 byte 超過（空白でも）は拒否」を正確に分離する。trip 検出は adapter 側 flag（`was_limit_exceeded`）を正本として backend が wrap した io error を `LimitExceeded` に再分類する。依存は `=` pin + 公開 7 日経過ポリシーで、serde_json =1.0.154・serde-saphyr =2.0.0・toml =1.1.8 を採用した。serde_yaml 0.9.x は unmaintained（archive）で不採用、unsafe-libyaml は unsafe 原則禁止で不採用、serde-saphyr は非実用選択肢がない中で budget 機構・MSRV 1.89・serde trait 境界を満たす唯一の実用 backend として採用（default-features=false+serialize/deserialize で最小導入）した (Issue #297)。

正直な error 分類の原則は「虚偽の kind 化をしない」である。JSON depth overflow は serde_json が固定内部上限（128）しか持たず公開 knob 化は虚偽の保証になるため `Syntax` 分類+文書化で対応し `LimitExceeded` に偽装しない。TOML 文法には「文書後の余剰」と「文法違反」の区別がないため trailing data は `TrailingData` ではなく `Syntax` と正直に分類し、`toml::from_str::<Table>`→`try_into::<T>` の 2 相で文法違反（`Syntax`）と型不一致（`DataModel`）を位相分離する。YAML は `MultipleDocuments`→`TrailingData`、`Budget` breach→`LimitExceeded`（breach から limit 名と実効上限を `DocumentError::limit()` へ写像）、未知 variant は non_exhaustive 前提で `Syntax` へ保守 fallback。snippet 漏洩防止は YAML `with_snippet=false`、TOML は backend `Display` が入力行を含むため `source()` に `BackendMessage`（`message()` テキストのみ）を載せる wrapper で行う (Issue #297)。

CSV streaming は `csv::Reader` ではなく `csv-core` の pull-based parser を caller 所有 buffer 駆動で回す `CsvReader`/`CsvRecord`/`CsvWriter` の二層構成を採用した。`csv::Reader` は内部 `Vec<u8>` を自動成長させ field/record byte 上限を割当前に強制する経路がないため不採用である。`Preserve` BOM policy は csv-core が最初の `read_record` で 3 byte 以上あれば無条件に UTF-8 BOM を strip する内部挙動への対処として、最初の parser 投入を 2 byte に cap する `bom_guard` で回避した（workaround は refill 内 1 条件に隔離）。`refill` 条件を `!exhausted || prefix 未消化` に修正し、probe が短い入力で先に EOF へ到達した場合に prefix 残留 byte が parser に届かず末尾 record を drop する実害 bug を解消した。backend grammar は permissive（未閉鎖 quote 受理）のため strict quote 検査の独自実装は二重責務として棄却し事実を文書化し、formula injection は変換しない（sanitizer ではなく consumer 責務）。`read_typed` は完全 record 取得後に `csv::StringRecord` 経由で deserialize し非 UTF-8 field は `InvalidEncoding`（部分値を返さない）(Issue #298)。

XML は read 専用 streaming とし、write 系 machinery の cfg に xml を含めない。`XmlEventReader<R: BufRead>` が caller 所有 `XmlEventBuffer` へ借用 event（`XmlEventRef<'_>`）を供給し `to_owned()` で所有 `XmlEvent` へ切り離す。design では resolver 借用と event 借用の競合を `read_event_into`+手動 `resolver().resolve_*`+aux buffer コピーで解決する想定だったが、実装で backend の `BytesStart::name()`/`attributes()` が `&self` 束縛で `'b` を取り出せない（buf/name_len は pub(crate)）と判明し aux buffer を廃止した。名・属性値・URI・宣言/PI 文字列は `Cow<'a>` 型のまま Owned コピーとし、大きい payload（Text/CData/Comment）のみ `into_inner`/`xml1x_content` で真の借用を維持する構成に変更した。`max_event_bytes` は公開後に `raw.len()` を読めないため `buffer_position()` 差分計測で同義の幅を計測し「公開前検査」契約を維持するが、実態は backend 内部 buffering 後の公開時検査であり確保前の厳密 cap ではないと正直に文書化した。`XmlEventReader::new` は BOM probe 等の先読みを行わないため Result ではなく Self を返す infallible（csv の eager probe との差異）で、一度の Err 後も reader を再使用させない failed poison latch を追加した (Issue #299)。

serde 語彙の移行は 2 段階で行った（Issue #725）。`EnvironmentKind::RealAbiTestPlugin` の serde 語彙 gap（emit `real-abi-test-plugin` vs schema 語彙 `test-plugin`）に対し、Phase A は `#[serde(alias = "test-plugin")]` で deserialize 側のみ両綴り受容（`#[serde(alias)]` は deserialize 側のみ作用し serialize 出力を変えない — serde の仕様）。emit flip は `environment_kind_serde_matches_as_str`（serde emit↔`as_str()` 一致を全 variant で強制）により serde rename+`as_str()` flip+plugin-dock-test 更新を同一 slice で不可分にする必要があったため第 2 slice に分離した。Phase B は `#[serde(rename = "test-plugin", alias = "real-abi-test-plugin")]`+`as_str()` → `"test-plugin"` の atomic flip で、canonical=test-plugin（schema 正本 `ci/consumer-verify/evidence.mjs` の `ENVIRONMENT_KINDS` に収束）、`real-abi-test-plugin` は deserialize alias で恒久受容とした。consumer 影響評価では audio-lens・synvelis は metadata module/`EnvironmentKind`/`RunMetadata`/`environment_kind` を未消費（oracle/pcm/backend/clock のみ）で影響ゼロを確認した (Issue #725)。

## 圧縮フォーマット

gzip framing は flate2 高層 adapter（`MultiGzDecoder` 等）に委譲せず、`Compress`/`Decompress`/`Crc` 低層 primitive のみに閉じ込め、gzip の header（FEXTRA/FNAME/FCOMMENT/FHCRC・`MEMBER_HEADER_MAX=64KiB`）/trailer（CRC32/ISIZE）codec と member framing・byte accounting・state machine はクレート側で所有した。高層 adapter では member 境界・消費 byte・未読 BufRead 保存・scope 別 trailing 判定を呼出し側に提供できないためである。公開面に flate2 型・version を出さず、`io::Error` に包んでも `source()` 経由で kind を復元できる変換規則とした (Issue #300)。

Encoder は `Writing`→`Finishing`→`Finished`|`Failed` の状態機械で、`finish()` は trailer/stream-end を emit し receipt を返す唯一の成功証明で冪等（保存 receipt を返す）、`flush` は deflate sync flush であって完了ではなく、Drop は一切 write しない（未完了 trailer が黙って付かない）、失敗は terminal `Failed` に latch し以後 `InvalidState`。Decoder は `VerifiedEnd`（format 末尾・trailer/checksum・scope の入力境界契約が全成立）のみ `Ok(0)` を返し、`read(&mut [])` は状態を変えず EOF 根拠にせず、`finish()` は `VerifiedEnd` のみ `Ok(DecodeReceipt)` で途中は `NotExhausted`。`DecodeScope` は `SingleUnit`（最初の member のみ・後続 byte は呼出し側 BufRead に残す）/`WholeInput`（連結 member を単一 stream 復号・member 末尾 trailing byte を `TrailingData` で拒否）である (Issue #300)。

実測由来の教訓が 2 つある。`Z_SYNC_FLUSH` 系 flush は呼出しごとに空 stored-block marker を必ず emit するため `made==0` を終了条件にすると無限ループになり、実測で test process が GB 級に膨張した — scratch を満たさない出力で打ち切る規則に修正した。`DeflateIn::pump` は入力を eager に消費する decompressor が内部 pending output を残したまま source starvation に誤判定されるのを防ぐため、空 input でも `decompress()` に掛けて内部出力を先に drain してから初めて starvation を報告する。gzip member 境界は `BufRead` が `fill_buf` で `[0x1f]` のみを返す合法ケースを EOF/trailing と誤認しないよう 2 byte magic を明示消費してから残り固定 8 byte を読む (Issue #300)。

failure 試験は write ではなく flush/finish で誘発する。compressible 入力は backend 内部にバッファされ小さな write が failing writer に届かない（非決定的）ため、sync flush/finish は必ず byte を emit する確定的な失敗入口として試験に使う。budget は累積 semantics で上限ちょうどの byte は正当に配信し次の read/write で違反を報告する — 試験側も「違反は次の操作で表面化」を検証する。CPU 時間・backend 内部メモリの hard limit は宣言せず累積 byte/unit budget のみ強制する（zip-bomb 対策は呼出し側の `DecodeLimits` 設定に委ねる）(Issue #300)。

zstd（Issue #301）では private `trait OutPump`（`feed`/`flush_sync`/`finish`）を導入し `EncoderCore<W, P: OutPump>` に一般化して flate2/zstd で共有した。zstd backend は `zstd-safe` を `default-features = false`（vendored C を `cc` でビルド）で採用した。`decompress_stream` が frame end で消費を止め `InBuffer.pos` で byte-exact な消費量を返すため、呼出し側 BufRead の prefetch と receipt 会計を分離できる。高層 zstd crate の stream adapter は内部 buffering と Drop-write があり frame 境界・`SingleUnit` の後続 byte 保持・「Drop は書かない」契約を保証できないため dev-dep（参照実装）に限定し、ruzstd（純 Rust decoder）は byte-exact な frame 境界消費量の取得 API がなく receipt 契約を満たせず棄却した。FHD parser は ≤18B の stack buffer に限定し boundary scan で frame 境界を検出、`DParameter::WindowLogMax` と header-parse window 強制で展開 window を制限し、`max_window_log` の既定は `WINDOWLOG_LIMIT_DEFAULT`、範囲外は `InvalidInput` で拒否。backend error は `get_error_name` を `source()` に保存して分類し Negative test で pin する。skippable frame は data unit に計上しないが、その byte は圧縮入力 budget には計上する（境界消費は確かに発生するため）。1 回の `decompress_stream` が produced bytes と frame end を同時に返すケースがあり、produce を返す前に frame end を latch する必要があった — 初期実装は end を落として次回 read が `TruncatedInput` になる不具合を test で捕捉・修正した (Issue #301)。

fault fixture は「byte を吐く最初の呼出」で駆動し write 回数仮定が backend でずれるリスクを「試験が fail して検出される設計（偽装 pass しない）」で受けた。`FailAfter.inner` で受理 byte を保持するよう強化し、`FailFlush`（flush 常時失敗）・`RecoveringWriter`（`new`/`after_ok` で失敗窓制御）・`FailingReader`（`fail_at` 以降 `ConnectionReset`）を新設した。高圧縮率 budget 試験は ~1MiB zeros（実圧縮 <1/100 を fixture 自体で assert）で「本当に展開が起きる」ことを保証した (Issue #285)。

## アーカイブ形式

IO-04 横断設計は、形式別 Reader/Writer/Entry 契約（ZIP は `Read+Seek` indexed・TAR は `Read`/`Write` streaming の API 族）・共通 format 中立型（形式が実在する情報のみ記録）・外部 `zip`/`tar` クレート非採用で内部 Parser+非公開 codec・Serde 非依存・`std::io` ベース・`source()` のみ診断を固定した。所有権/状態機械は Entry 排他借用・明示 `finish` のみが完了証拠・TAR `Ready`/`EntryOpen`/`Pending`/`Failed`・`discard_pending`/`discard_remaining`・Writer poison とし、Receipt は `ArchiveReadReceipt`/`EntryReadReceipt` の typed summary・`verified: bool` 非丸め・真正性≠整合性を含む (Issue #286)。

Secure Extraction は信頼モデル・Path Policy・canonical 衝突・kind/budget・OS/FS 別保護レベル表・TOCTOU 境界・Cleanup/Recovery を含む。`openat2`/`RESOLVE_BENEATH`/`cap-std` 採用は Deferred（現行の dirfd/handle 相対+no-follow+CreateNew+identity 照合で主要脅威をカバー）とし、ZIP64・sparse/special/link・Directory 原子的 Publish・永続 Recovery Journal も Deferred。終了/公開契約は Entry→Archive→Compression→StagedFile publish の finish 連鎖分離・`ExtractedTree`≠Directory Publish・無条件 Atomic Directory Publish 非保証・tar.gz/tar.zst の 2 層 finish 独立・ZIP 内部 codec の capability 閉じ込め・IO-03 への必須依存なしを定めた (Issue #286)。

ZIP reader（Issue #302）は EOCD 末尾探索→budget 前検査→中央 Directory 一括解析→open 時 Local Header 照合という lazy な検証段階分け（「index は構造、payload は検証」方針）を採用した。EOCD 探索は後方向の「signature + comment_len 完全一致」規則で fail-closed（細工された comment 内偽 signature は後続 CD 解析で失敗に倒れる）。cap 到達時に source を 1 byte probe し、追加出力があれば hard_cap<declared なら `LimitExceeded`・等しければ `SizeMismatch` として宣言超過と budget 超過を区別する。`verify_all` は部分 receipt ではなく最初の entry 失敗（`ChecksumMismatch`）を返し entry 単位の verified 状態は正直に残る。`into_inner` は inner stream を返すが検証ではなく完了証拠でない。依存は `crc32fast`+`flate2`(rust_backend) に限定し Backend 型を公開 API に出さない (Issue #302)。

ZIP Writer は `EntryWriter.finish` が Entry 構造を、`ZipArchiveWriter.finish` が CD/EOCD を確定する型分離 API とし、Entry を finish せず Drop した Archive は `InvalidState` で非 Completed にする（poison）。「途中 Drop=無害な cancel」ではなく「partial bytes は既に sink に出たので archive 全体を完成不可にする」が正直な失敗分類（runtime poison で保証、型状態ではない）である。Local Header patch-back 方式を採用（data descriptor は出力しない）— `Write+Seek` が必須なので最も単純で広く読める形式。LFH 部分書き込み失敗時も archive を poison。`CountWrite` shim で deflate の実 compressed bytes を正確に計測（`DeflateEncoder` 内部 buffer は `finish()` で flush）。ZIP64 出力は非対応で超過時 `Unsupported` で早期分類 (Issue #302)。

TAR（Issue #303）は `src/tar/header.rs` に 512 block field 定数・checksum 検証/生成・octal/base-256 数値・USTAR magic 判定・PAX record parse・header 分解を実装し、共通型は最小拡張（`ArchiveEntryInfo.link_name`・`EntryReadReceipt.disposition`）に留めた。`TarArchiveReader<R: Read>` は `next_entry` が USTAR/GNU `L`/`K`/PAX `x` を実効値へ解決し、`S`/`3`/`4'`/未知 typeflag を `Unsupported`、構造欠陥を設計の kind へ分類。状態は `Ready`/`EntryOpen`/`Pending`/`EndSeen`/`Failed` で、途中 Drop→`Pending`→`discard_pending` で復帰、失敗時 `Failed` latch。`TarEntryWriter` は宣言 size で write を cap し、実書込<宣言での `finish` や未 finish Drop は archive を poison。header は USTAR（name ≤100・prefix 分割）を基本とし、長名・octal 上限超過 size は PAX `x` Entry を先行出力する (Issue #303)。

`SafeRelativePath`（`ArchiveName -> SafeRelativePath`）を唯一の検証入口とし、`..`/絶対/drive/UNC/`\`/`:`/予約名/末尾 `.`/末尾空白/NTFS 禁止文字/空・`.` component/非 UTF-8/NUL を拒否する。canonical 衝突キーは NFC+lowercase で、casefold・NFC/NFD 差・同一 entry が同一 key に畳まれる。PAX `path` record は ustar header 名を完全置換するが `SafeRelativePath` policy を迂回できない（hostile `path` も `InvalidInput` 拒否 — extension 由来名の迂回防止）。nested archive（ZIP-in-ZIP）は再帰展開されず byte 列として opaque に書き出される (Issue #304, Issue #286)。

OS 別 staging backend は unix が dirfd/`openat`/`O_NOFOLLOW`/`O_CREAT|O_EXCL`、windows が `NtCreateFile`/`NtOpenFile`/`NtDeleteFile`+`RootDirectory`/`OBJ_DONT_REPARSE`/`FILE_OPEN_REPARSE_POINT` で `StagingDir`/`StagingFile` を実装し、cleanup は records の node identity 照合付き降下削除で、差し替えられた node は消さず retained 報告とする（symlink/junction/foreign dir 差し替えを試験で pin）。`canonicalize_handle` を持たない backend で re-root は `Unsupported`（path rebind 禁止・黙示縮小禁止・Weak 一律拒否禁止）とした。`ExtractionFailure` が `Option<ExtractionRecoveryHandle>` を同梱し失敗後も `inspect`/`cleanup` が動く。`ExtractedTree` の非不変性と Source 改変 race は保証外として rustdoc/README に明記する (Issue #304, Issue #409)。

## 検証・証拠の運用

docs chain は spec→design→test-spec→plan→task の docs-only slice で設計を正本化し、その後 `src/` 実装と設計正本の照合・契約試験棚卸し・不足試験追加の slice を実施する 2 段階パターンで進行した (Issue #284, Issue #285, Issue #286)。

feature matrix の個別 `cargo check`/`test` は「canonical でない補助検証として明記」し、canonical は CI lane とする。workspace test task は default features のみを対象とするため feature-gated code の検証は各 Issue で補助実行+必要に応じて専用 mise task/lane を追加する。`test-io-msrv` lane は test 実行のみで clippy を含まず（`test-ofx-msrv`/`test-ui-test-msrv` と同範囲）、`mise exec rust@1.89.0`+`CARGO_TARGET_DIR` 分離で dev target と分離した。io-e2e を同一 `-p` 集合に含めると resolver v2 の feature unify で io-structured 全 format と io-compression gzip,zstd が MSRV build に載ることを実測で確認し、E2E 消費 feature と deflate 補完の分離を検証した (Issue #297-#300 共通, Issue #306)。

依存追加は公開から 7 日経過・MIT OR Apache-2.0・`=` pin が原則。並行 worker が `Cargo.toml` members・`crates/README.md`・`Cargo.lock`・`ci/impact/map.mjs`・`ci.yml`・`mise.toml` を同時編集し得るため、最終検証前に必ず `git fetch origin`→`git merge origin/main`→`Cargo.lock` 再解決（cargo 経由・手編集しない）を行う。mise task は array `run` ではなく `&&` 連結にする — `ci/impact` の lane-owner 導出が task body を最初の `[` で打ち切る regex parse するため array 形では `-p` 引数を捕捉できず lane が「常に expected」に退化する (Issue #297-#300 共通, Issue #300)。

検証の誠実性ルールは「未実測を PASS にしない」で一貫する。`not run`/`NotRun`/`Unsupported`/`Deferred` を PASS に繰り上げず、実 OS 誘発不能・未実測環境・consumer 実測・実 4GiB・Network/Cloud FS・macOS/Linux は正直に記録する。canonical な検証は mise lane とし、`cargo tree` や grep・`std::any::type_name` audit による補助証拠は「補助と明記」して格付けする。CI 証拠は対象 SHA の completed run を必須とし、直近 run の差分ゼロ確認は「補助証拠」として採用するが Pass に繰り上げない (Issue #288, Issue #306, Issue #251, Issue #398/#400)。

実 OS で誘発不能な fault（`Indeterminate`・publish 後 DirSync 失敗・`TempState::Unknown`・phase 別 `NotPublished`）は、実 FS fixture（OS が制御不能に返すため不可）・io-e2e 側 mock 複製（oracle 二重化で pipeline との乖離を検出不能）・公開 API への fault 注入点追加（「公開 API を変えない」制約違反）の 3 案を棄却し、既存 `#[cfg(test)]` mock を `cfg(any(test, feature = "fault-injection"))`+`#[doc(hidden)]` facade で opt-in 公開する形状を採用した。facade の公開 signature は std 型と公開 result 型のみで `PlatformFileOps`/`StageOwner`/`RecoveryInfo` 等の private 型を出さず `private_interfaces` lint を構造的に回避した。`MockPublish.physically_applied` を report から独立した軸にして「Unknown 報告だが物理的には適用済み」の正直なモデルを可能にした (Issue #306)。

敵対的 fixture（ZIP symlink/special entry・traversal・破損 checksum 等、公開 writer が生成できない bytes）は `tests/common` の byte-exact helper（`crafted_tar_entry`・ZIP CD `external_attrs` patch）で構築し、本番 API・`#[cfg(test)]` mock には触れない。実装詳細に結合しない budget 試験の書き方として、`ZipArchiveReader::new` が `max_entries` を indexed open 時に enforce する実装を確認し entry-count budget 試験は reader/extraction どちらの typed limit 失敗でも受理する形にした。Windows の delete-pending semantics により open handle 保持中の directory は `try_exists` に残るため、extraction tree 検証では `RootedDir`/file handle を cleanup 前に解放する scope を設けた (Issue #306)。

bounded corpus replay は固定 seed `0x52463346555a5a45`・48 cases/format×9 形式・`INPUT_CAP=256KiB`/`DECODED_CAP=1MiB`/`DEADLINE=120s` の `#[ignore]`+`mise run test-io-e2e-corpus` opt-in lane とした。PRNG は依存追加を避けるため splitmix64 を test file 内に実装し、変異は byte flip/truncate/extend/splice の 4 系統を決定的に選択。panic は reject と区別するため `catch_unwind` で計数し合計 0 を assert（panic hook は計数中のみ無音化し必ず復元・`resume_unwind` で再送出）(Issue #306)。

実 4GiB 試験はサイズ×シナリオの直積を個別 `#[test]` にすると ignored test が 15 個に増え preflight も各 test で重複するため、単一 `#[ignore]` test+内部シナリオ表（4GiB−1/4GiB/4GiB+1×5 scenario=15 case）に集約した。checksum は新規依存なしの chunked FNV-1a（`DefaultHasher` は実装詳細が安定でないため公開定数の自前実装）を 4MiB chunk で畳み込み、payload は位置依存 `mix64` pattern で write/readback を照合。scenario 関数を `Result<(),NotRun>` にし `StorageFull` と `FileErrorKind::Io`/`Unsupported` の OS 起因失敗を `NotRun` へ写像し、`InvalidInput` や assertion 失敗は通常 panic（Fail）として残し契約違反と環境不足を分離した (Issue #306)。

`with_borrowed_demuxer`（Issue #400）は `&mut (impl Read + Seek + ?Sized)` を `&mut dyn Demuxer` の scoped closure へ接続し、`std::thread::scope` で worker（`open_demuxer(proxy)`→`f`）を spawn し呼び出し側で `serve` を回す。`Req`/`Resp` enum を `SyncSender`/`Receiver` で結び `CHUNK=64*1024` で巨大 read 要求を短い逐語 read 列に変換（`Ok(short)` 許容 contract で `MediaSourceStream` の read-ahead 挙動を維持）。追加メモリ O(1)。`f: Send`+`R: Send` のみ要求し `!Send` な外部参照を `f` 内で直接呼べない制約があり、`f` 内は decode/pump のみに留め `Send` でない後処理は scope 外に置く。`&mut dyn Demuxer` handout は escape 不能（`compile_fail` doctest で固定）、unsafe なし・依存追加なし。`SourceReader` → `SourceReader<'a>` の一般化は機械的注釈で互換維持（bare `SourceReader` を書く consumer は `<'static>`/`<'_>` 注釈が必要で互換破壊として PR に明記）(Issue #400)。
