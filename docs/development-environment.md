# 開発環境・CI リファレンス

この文書は [AGENTS.md](../AGENTS.md) の `### 検証入口` セクションから分離した詳細リファレンス（規約でなく詳細情報）です。
各項目の正本は対象の基盤ファイル（`mise.toml`・`.github/workflows/*.yml`・`.pre-commit-config.yaml`・`.gitattributes`・`apm.yml`・各 lockfile）であり、本書はそれらを横断した consolidated な説明です。齟齬がある場合は正本ファイルを優先します。

## 検証入口（AGENTS.md から分離したセクション）

concurrency group（`pull_request` では `${{ github.workflow }}` + `refs/pull/<N>/merge`・`cancel-in-progress: true`）で新 run 開始時に cancel され、`push` to main・`workflow_dispatch`・別 PR の run は run ごと一意の group `docs/designs/issue-333-impact-based-ci.md`・`docs/designs/issue-346-ruleset-migration-runbook.md` に残る。別 workflow の `.github/workflows/consumer-verify.yml`（Issue #219 Cross-Repo 検証 lane）は `workflow_dispatch` 専用の情報 lane で required checks に含めず、片 Consumer の失敗・未検証が他 Consumer や merge を止めない。両 Consumer lane は scratch checkout 内で ruviform git 依存を候補 rev に正規化（rev pin・branch 追従・rev 未指定を同一ルールで処理）し、単一 SHA lockfile guard 後に consumer 側 mise task（audio-lens: `check-ci`/`al-cli` ci build/`check-cli-headless`/`test-ci`、synvelis: `check`/`test`）を実行する。実行は access mode で分岐する（design ## mise タスク体系

- タスク一覧・実行内容・`description` の正本は `mise.toml`。`mise tasks` で全タスクと説明を一覧できる。
- freshness 付きタスク（`install-ui-*`・`build-ui-*`）は `sources` / `outputs` 宣言が不変なら skip される。`install-ui-*` は `sources` = package-lock + package.json、`outputs` = `node_modules/.package-lock.json`（npm が node_modules に必ず書く隠し lockfile）で lockfile 単位の `npm ci` を 1 回に集約する（Issue #330）。verify 系タスクは `depends` 経由で install/build を再利用し、fresh なら実行・不変なら skip される。
- `install-ui-browser-chromium` には mise freshness を付けない。browser path は `PLAYWRIGHT_BROWSERS_PATH` 依存のため、mise の sources/outputs ではなく Playwright 自身の per-revision 存在確認を authoritative skip とする（Issue #332）。
- `build-ui-*` の `tsc` dist 出力は `rewriteRelativeImportExtensions` で `.ts` → `.js` specifier を書き換える。`build-ui-showcase` は showcase + core + components + viz + binding の src を横断する複合 dist（rootDir `..`）を出力し、`ui/browser-test` はこの dist 宣言へ typecheck する（`depends` で showcase build を pin。Issue #310/#330）。
- `test-rt` は `rt_` プレフィックス命名の RT 契約テストを名前フィルタで選択する（Issue #18・#21・#26 で導入後、media-core・dsp・audio-analysis・plugin 系・math::dsp・audio-device 等の RT-suitable API を持つ各クレートへ順次拡大済み）。0 件一致でも成功するため RT テスト未存在時はスキップ相当。
- `bench` は全量計測入口（計測時間が長いためローカル手動実行向け）、`bench-smoke` は各ベンチを計測なしで 1 回実行するスモークで CI `bench` ジョブが呼ぶ入口。
- `check-ci` は CI verify lane に含まれない単独タスク（Issue #331 で `lint-ci` に統合済み）。clippy-driver 差分の切り分け等、素の rustc にだけ通したいローカルトリアージ向け。
- `test-l1-real-plugin` / `lint-l1-real-plugin` は実規格プラグイン L1 E2E opt-in lane（Issue #114）。fixture cdylib + `host` feature runner bin を要し `#[ignore]` + `#![cfg]` + `required-features` で既定経路（`cargo test --workspace`・既定 `lint`）から分離。CI `l1-real-verify` ジョブが呼ぶ入口。
- `test-ci-summary` は `ci/summary/` の needs 結果判定表 + `expected_sha` dispatch 契約 + report 形状の contract test（Issue #366。CI `ci-summary` ジョブが verdict 出力前の自己検証として呼ぶ。node toolchain 必須）。
- `*-ui-webview` タスクは Issue #156 の webview feature lane（既定の `check`/`lint`/`test` の feature 集合外）。`rvf://` スキーム/data 面は headless 検証可能、窓付き実動作は手動検証。Linux では `libwebkit2gtk-4.1-dev` + `libgtk-3-dev` が必要（CI `ui-verify` ジョブが導入）。
- 上記表に未収録の opt-in タスク（`mise tasks` で確認可能）: `test-plugin-core` / `lint-plugin-core`（plugin-core 契約テスト・lint）、`test-ofx` / `lint-ofx` / `test-ofx-bridge`（OFX host 系テスト・lint・C bridge ネイティブスモーク）、`test-video-proc-icc` / `lint-video-proc-icc`（video-proc の icc feature lane、CI `icc-verify` ジョブが呼ぶ）、`test-ofx-msrv`（MSRV 1.89 toolchain 上での plugin-core / OFX テスト。`mise exec rust@1.89.0` 経由、成果物は `target/msrv-ofx/`）。

## CI ワークフロー構成（`.github/workflows/ci.yml`）

- トリガ: `pull_request`（types: opened/synchronize/reopened/ready_for_review/edited — `edited` は base retarget の再実行に必要）・`push`（`main`）・`workflow_dispatch`。`main` の required checks として lane job 9 context（ruleset `main-checkstatus`・macOS legs は Issue #333/#326 で PR Required から物理分離済み）+ 終端 `ci-summary` が全 lane（macOS legs 含む）の終了を `if: always()` で待つ fail-closed 集約として報告される（Issue #366 Stage 1。`ci-summary` 単一 required 化は Owner が ruleset を更新する後続 stage — Stage 1 では非 required で、9 lane context は required のまま。`docs/designs/issue-366-full-ci-stage1.md`）。
- 同一 PR の run は concurrency group（`pull_request` では `${{ github.workflow }}` + `refs/pull/<N>/merge`・`cancel-in-progress: true`）で新 run 開始時に cancel される。`push` to main・`workflow_dispatch`・別 PR の run は run ごと一意の group のため cancel されない（Issue #328）。
- `verify`（`fmt-check` → `lint-ci` → `test-ci` の step 列）: Issue #331 で `check-ci` は `lint-ci` に統合済み — clippy-driver が rustc 全診断 + clippy lint を発行するため独立 `cargo check` step は同一ユニット集合の二重 frontend 評価だった。`mise run verify-ci` も同一列。
- `l1-real-verify`（`mise run test-l1-real-plugin` + `mise run lint-l1-real-plugin`）: Issue #114 の実規格プラグイン lane。
- `ui-verify`: `check-ui-webview`/`lint-ui-webview`/`test-ui-webview`（Issue #156 webview feature lane）、`check-ui-headless`/`test-ui-headless`（Issue #258 `ui/core` headless 契約 lane）、`check-ui-components`/`test-ui-components`/`build-ui-components`（Issue #259 `ui/components` Web Components lane）、`check-ui-viz`/`test-ui-viz`/`build-ui-viz`（Issue #260 `ui/viz` Reference Viz lane）、`check-ui-binding`/`test-ui-binding`/`build-ui-binding`（Issue #261 `ui/binding` Command/Query binding lane）、`check-ui-guitest`/`test-ui-guitest`（Issue #311 `ui/guitest` 決定的 GUI テスト基盤 lane）、`check-ui-showcase`/`test-ui-showcase`/`build-ui-showcase`（Issue #263 `ui/showcase` ショーケース/検証 fixture lane）、`check-ui-browser-test`/`test-ui-browser`（Issue #310 `ui/browser-test` 実ブラウザ lane）で `test-results/` を artifact upload する。
  - Linux はジョブ内で WebKitGTK 開発パッケージと Playwright browser system deps を導入（browser binary とは別レイヤーで毎 run 実行）。
  - browser binary は `PLAYWRIGHT_BROWSERS_PATH`（workspace 内 `.cache/ms-playwright` に pin）を `actions/cache` で Playwright version・Chromium revision・OS/arch 紐づけ key で復元し、準備 step（`install-ui-browser-chromium`）と launch 検証 step（破損復元時は wipe+reinstall fallback）を挟んで `test-ui-browser` を実行する（Issue #332）。
  - ジョブは検証 lane の前に `mise run setup-ui` を 1 ステップ実行し、各 `ui/*` package-lock の `npm ci` を 1 回に集約する（Issue #330。verify タスクは freshness 付き `install-ui-*` を `depends` で再利用）。
- `verify`・`l1-real-verify`・`ui-verify` の required legs は `ubuntu-latest` / `windows-latest` の 2 OS matrix（`verify` のディスク計測ステップは ubuntu のみ）。macOS legs は `verify-macos` / `ui-verify-macos` / `l1-real-verify-macos` の別 job（Issue #333/#326 で物理分離・#366 Stage 1 でも別 job を維持。required ではないが `ci-summary` が全結果を集約）。`rt-verify`（`mise run test-rt`）・`icc-verify`（`test-video-proc-icc`/`lint-video-proc-icc`）・`compression-verify`（`check`/`test`/`lint-io-compression`・Issue #300/#301）・`io-structured-verify`（`check`/`test`/`lint-io-structured`・Issue #364 で新設の format feature lane）・`bench`（`mise run bench-smoke`）は `ubuntu-latest` 単独。
- sccache: `verify`・`ui-verify` では `RUSTC_WRAPPER` として GitHub Actions cache backend で先行導入（Issue #329。`rt-verify`・`icc-verify`・`l1-real-verify`・`bench` は効果確認後の段階展開のため未適用）。repo variable `CI_SCCACHE_DISABLE=1` で全 sccache step を skip して即時無効化できる。
- Issue #366 Stage 1（rev 2026-11-05）で選択実行機構は撤去済み: `impact` 分類 job・`ci/impact/` 一式・`CI_IMPACT_DISABLE`・lane ごとの選択 `if:`・`macos-report`・`ci-gate` を廃止し、全 lane が全 trigger で無条件実行される Full CI へ移行した。
  - 終端 `ci-summary`（`if: always()`・全 lane を `needs` に含む）が `needs` context + 実測 checkout 証跡の純関数として全 lane の `success` を要求する fail-closed 集約（`ci/summary/summary.mjs`）。failure/cancelled/skipped/not-run/unknown は全て Fail — skipped job を成功扱いしない。job 内で `test-ci-summary` による自己検証を先に実行し、verdict・実測共通 SHA・expected SHA・event SHA・summary checkout・workflow revision・job 別結果・leg 別 checkout 表・run URL を Job Summary + `ci-summary-report-attempt-<n>` artifact に記録する。
  - SHA 証跡（rev 2026-11-05）: 全 lane job は checkout を `ref: ${{ github.sha }}` に pin（pull_request/push では既定と同義、workflow_dispatch で lane ごとの ref 浮動を排除）し、直後に `git rev-parse HEAD > checkout-sha-<leg>-attempt-<n>.txt` を記録して同名 artifact upload（matrix leg は `CHECKOUT_LEG` env で `<job>-<os>` を、artifact 名は `github.run_attempt` で attempt を一意化 — upload-artifact v4 は名が run 単位で一意のため rerun 衝突を防ぎ全 attempt の証跡を保全）。`ci-summary` が `download-artifact`（`pattern: checkout-sha-*` + `merge-multiple`）で集約し、宣言 14 leg 分の存在・形式・leg ごとの最大 attempt 選択（`needs` 結果と同じ最新 attempt 基準）・一致を fail-closed で検証する — lane が緑でも実測証跡を出せない run は Fail。同一 leg の attempt 間 sha 乖離・命名規約外の証跡も Fail。`github.sha`（event sha）は裏付け anchor、`github.workflow_sha`/`workflow_ref`（workflow revision）は記録のみで、検証 revision の定義は実測値のみ。
  - `workflow_dispatch` は `expected_sha` 入力で dispatch 契約を持つ（Issue #367 daily-ci 連携。入力時のみ照合、空なら照合なし）。照合対象は全 lane leg の**実測 checkout 共通値**であり `github.sha` の代理比較ではない — 実測不能・不一致は Fail。
  - macOS legs は別 job のまま `ci-summary` の `needs` に含まれる（PR required ではないが失敗・未実行は run を赤くし、runner 逼迫による queue→cancel は `cancelled` として Fail 判定）。
  - `ci-summary` 単一 required context への移行は Owner が ruleset（`main-checkstatus`）を更新する後続 stage。Stage 1 では `ci-summary` は非 required で、9 lane context は required のまま（正本: [docs/designs/issue-366-full-ci-stage1.md](designs/issue-366-full-ci-stage1.md)。旧選択実行の設計・移行経緯は [docs/designs/issue-333-impact-based-ci.md](designs/issue-333-impact-based-ci.md)・`docs/designs/issue-346-ruleset-migration-runbook.md` に残る）。
- `.github/workflows/consumer-verify.yml`（Issue #219 Cross-Repo 検証 lane）は `workflow_dispatch` 専用の情報 lane で required checks に含めず、片 Consumer の失敗・未検証が他 Consumer や merge を止めない。両 Consumer lane は scratch checkout 内で ruviform git 依存を候補 rev に正規化（rev pin・branch 追従・rev 未指定を同一ルールで処理）し、単一 SHA lockfile guard 後に consumer 側 mise task（audio-lens: `check-ci`/`al-cli` ci build/`check-cli-headless`/`test-ci`、synvelis: `check`/`test`）を実行する。実行は access mode で分岐する: `CROSS_REPO_DEPLOY_KEY` secret 設定済みなら SSH Deploy Key 経路（private 前提の canonical 経路）、未設定でも対象 repo が public で匿名 HTTPS read 可能なら secret 不使用の anonymous 経路で lane を実行、どちらも不可なら `not run`。全 lane `not run` → workflow 失敗（証拠ゼロを緑にしない）。
- `.github/workflows/consumer-impact-check.yml`（`pull_request`・draft 除外で PR 本文の Consumer 影響分類欄を機械検査していた非 required lane）は Issue #366 Stage 1 で撤去済み — 分類要件は `PULL_REQUEST_TEMPLATE.md` + レビュアー human gate に残る。

## Consumer 影響分類の運用（Issue #219）

公開 API / feature / behavior / dependency / CI 基盤の変更 PR は本文の Consumer 影響欄で Synvelis・AudioLens を独立して `impacted` / `no impact` / `unknown` に分類する。`unknown` 残置は互換性未確認であり、merge 前にレビュアーが分類欄の記入と `unknown` 解消先リンクを確認する（required check 化していないため human gate）。記入有無・`unknown` 解消先・分類内容の妥当性の確認は全てレビュアーが担う（機械検査 lane は Issue #366 Stage 1 で撤去）。PR 本文の記入形式は `.github/PULL_REQUEST_TEMPLATE.md` が正本。
