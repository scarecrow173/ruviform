# 開発環境・CI リファレンス

この文書は [AGENTS.md](../AGENTS.md) の `### 検証入口` セクションから分離した詳細リファレンス（規約でなく詳細情報）です。
各項目の正本は対象の基盤ファイル（`mise.toml`・`.github/workflows/*.yml`・`.pre-commit-config.yaml`・`.gitattributes`・`apm.yml`・各 lockfile）であり、本書はそれらを横断した consolidated な説明です。齟齬がある場合は正本ファイルを優先します。

## mise タスク体系

- タスク一覧・実行内容・`description` の正本は `mise.toml`。`mise tasks` で全タスクと説明を一覧できる。
- freshness 付きタスク（`install-ui-*`・`build-ui-*`）は `sources` / `outputs` 宣言が不変なら skip される。`install-ui-*` は `sources` = package-lock + package.json、`outputs` = `node_modules/.package-lock.json`（npm が node_modules に必ず書く隠し lockfile）で lockfile 単位の `npm ci` を 1 回に集約する（Issue #330）。verify 系タスクは `depends` 経由で install/build を再利用し、fresh なら実行・不変なら skip される。

  - SHA 証跡（rev 2026-11-05）: 全 lane job は checkout を `ref: ${{ github.sha }}` に pin（trigger snapshot への pin — dispatch 時点の ref head に固定し lane job ごとの開始時刻差による ref 浮動を排除）し、直後に `git rev-parse HEAD > checkout-sha-<leg>-attempt-<n>.txt` を記録して同名 artifact upload（matrix leg は `CHECKOUT_LEG` env で `<job>-<os>` を、artifact 名は `github.run_attempt` で attempt を一意化 — upload-artifact v4 は名が run 単位で一意のため rerun 衝突を防ぎ全 attempt の証跡を保全）。`ci-summary` が `download-artifact`（`pattern: checkout-sha-*` + `merge-multiple`）で集約し、宣言 14 leg 分の存在・形式・leg ごとの最大 attempt 選択（`needs` 結果と同じ最新 attempt 基準）・一致を fail-closed で検証する — lane が緑でも実測証跡を出せない run は Fail。同一 leg の attempt 間 sha 乖離・命名規約外の証跡も Fail。`github.sha`（event sha）は裏付け anchor、`github.workflow_sha`/`workflow_ref`（workflow revision）は記録のみで、検証 revision の定義は実測値のみ。

  - `ci-summary` 単一 required context への移行構想は ruleset 自体が不要になったため実質解消 — Issue #326 Stage 4 で `main-checkstatus`（9 lane required context）が disabled となり required checks は実効ゼロ、`ci-summary` は PR required context ではなく run レベルの fail-closed verdict として機能する（正本: [docs/designs/issue-366-full-ci-stage1.md](designs/issue-366-full-ci-stage1.md)・[docs/adr/issue-326-ci-yml-dispatch-only.md](adr/issue-326-ci-yml-dispatch-only.md)。旧選択実行の設計・移行経緯は [docs/designs/issue-333-impact-based-ci.md](designs/issue-333-impact-based-ci.md)・`docs/designs/issue-346-ruleset-migration-runbook.md` に残る）。
- `.github/workflows/daily-ci.yml`（Issue #367 共通 Daily Scheduler）は UTC `schedule`（`"17 21 * * *"` = 06:17 JST・分 != 0）と `workflow_dispatch`（`dry_run` 入力付き手動再判定）で起動する単一 `decide` job（ubuntu-latest・timeout 15 分）。required checks には含めない。
  - 権限: workflow 全体 `permissions: {}`、job は `contents: read`（script checkout）+ `actions: write`（`ci.yml` run 履歴 read + `dispatches` POST）のみ。`GITHUB_TOKEN` 以外の秘密・外部サービス・repository variable・DB を使わない — 状態正本は GitHub Actions 履歴そのもの。
  - `concurrency`: `daily-ci-decision` group で scheduler 自身を直列化し `cancel-in-progress: false`（判定〜dispatch 途中の打ち切りで証跡を失わない）。
  - 判定（`ci/daily/decide.mjs`）: `git/ref` で現在 `main` SHA を取得し、`ci.yml` run 履歴をページネーション取得（`branch=main` + per_page=100・上限 10 page）して `head_sha`+`head_branch`+event allowlist（`push`/`workflow_dispatch`/`schedule` — `pull_request` は構造上除外）で厳格同定。非対象除外は positive proof 制で、対象か否か立証できない record は `hold-unknown`（dispatch/skip-verified を禁止）。record が必須フィールドを欠く malformed response は `error`。"最新" は attempt 活動時刻（`created_at`/`run_started_at` — rerun は `created_at` を動かさない）で順序付け、tie・順序不能・`updated_at` が示す未解明の活動があると `skip-verified` に倒さず `hold-unknown`。最新 attempt が `completed`+`success` で一意に最新なら `skip-verified`、in-flight なら `suppress-in-flight`、未知 status/conclusion なら `hold-unknown`、既知の非 success/履歴なしなら retry 候補 — 同一 SHA の `workflow_dispatch` run は両 actor が識別可能な非 auto actor の場合のみ手動扱いで、それ以外（bot 片側・null/空/破損の片側未識別）は自動 dispatch として上限 2（初回+retry 1）に計上し `budget-exhausted` で警告（人力 rerun は budget を払い戻さない）。API 失敗・malformed response は `error`（job 失敗・fail-closed）、履歴打ち切り（`truncated`）は `history-truncated` で保留 — 不完全な履歴では success 判定・dispatch のいずれも確定しない。
  - dispatch: 直前に `main` ref を再照合（動いていれば新 SHA で再判定・有界。超過なら `main-moved`）してから `POST dispatches {ref: main, inputs: {expected_sha: <sha>}}` を発火し、新規 `workflow_dispatch` run の出現を有界 poll（既定 15s×最大 120s）で確認する。着地 `head_sha` が期待と違えば `dispatch-landed-mismatch`（その run は `ci-summary` の `expected_sha` 照合で Fail — 誤 SHA を検証済みにしない）、未観測なら `dispatched-unconfirmed`（eventual consistency を失敗と誤記しない）。scheduler の green run は「決定が完走した」ことだけを意味し、未検証状態は outcome・`::warning::`・`daily-ci-report-attempt-<n>` artifact（`kind: "daily-ci-decision"`）で可視化する。失敗 Issue への集約は #368 `ci-issue-tracker` の責務であり、本 workflow は Issue を作成しない。
  - 運用: 手動再判定は Actions → `daily-ci` → Run workflow（`dry_run` で dispatch なし判定のみ）。`budget-exhausted` からの復帰は原因修正後の main 更新（新 SHA で budget リセット）または `ci.yml` の手動 dispatch（ユーザ actor は budget 非計上）。定期 run は GitHub 障害で欠落し得て自己検出不能 — Job Summary/report の「最終成功検証時刻」（`latestVerified.updatedAt`）を日次確認の目安とし、長期欠落が疑われる場合は手動 `workflow_dispatch` で再判定する。外部監視の要否は後続判断（正本: [docs/designs/issue-367-daily-scheduler.md](designs/issue-367-daily-scheduler.md)）。
  - Consumer 採用契約（AudioLens/Synvelis 導入・Ruviform が汎用部分 Owner）: 再利用単位は `ci/daily/`（script+tests）+ `.github/workflows/daily-ci.yml` の vendoring で、Ruviform の Cargo/Frontend build/install・追加秘密を要求しない。env の `DAILY_TARGET_WORKFLOW`/`DAILY_MAIN_REF`/`DAILY_MAX_AUTO_DISPATCHES`/`DAILY_AUTO_ACTORS` を自 repo に合わせ、対象 `ci.yml` が `workflow_dispatch` + `expected_sha` 入力契約を持つことを前提とする（未対応なら照合保証なしの dispatch となる — 着地 SHA 報告のみで SHA race を観測）。`test-ci-daily` 相当の `node --test` を self-test として残す。

- `.github/workflows/ci-issue-tracker.yml`（Issue #368 CI failure Issue Tracker）は `workflow_run: {workflows: [ci], types: [completed], branches: [main]}` のみで起動する監視 workflow — `pull_request`/`push`/`schedule`/`workflow_dispatch` trigger を持たない。対象は「この repo・`head_branch == main`・event ∈ {push, workflow_dispatch}」の有効 Full CI 完了に限定（fork/PR/別名 workflow/scheduler 自身の run は skip）。`workflow_run.workflows: [ci]` は workflow **name** フィルタのため、`name: ci` を持つ別ファイル workflow が将来作られると event payload 側に混入し得る既知制限がある（履歴側は path/name で除外済み・Validator P2 として別途管理、現時点で同名 workflow は存在しない — `ci/tracker/README.md` の制約節参照）。job `track` のみ `contents: read`/`actions: read`/`issues: write` の最小権限で、`concurrency` による repo 単位直列化（`cancel-in-progress: false`）。`ci/tracker/tracker.mjs`（stdlib-only・`gh api` client 注入）は `workflow_run` payload を trigger とみなし、権威 run 履歴を取得して payload・marker 状態と突合してから判定する。失敗系結論で label `ci-failure`+scope marker 同定の未解決障害 Issue を 1 件に集約（初回作成・連続更新・複数 open は最小番号 canonical + duplicate close）、回復記録付き close は**最新証拠が記録最新失敗より曖昧なく新しい成功**（同一 run id 内は `run_attempt`、異なる run 間は `updated_at` で順序付け。同 id の失敗 a1→成功 a2 rerun は自分の失敗 attempt を閉じられる正当な回復）かつ `compare(失敗 sha→成功 sha)`・`compare(現在 main head→成功 sha)` がともに `{identical, ahead}` で、履歴に live `pending` run・識別不能 `unknown` record が残らない時のみ。cancelled/unknown/pending は operational 記録で close しない・古い成功で最新障害を消さない。手動 close 済み Issue は再 open しない・`diverged` は手動確認・Actions 全障害時は tracker も起動しない等の運用契約は [ci/tracker/README.md](../ci/tracker/README.md) が正本。設計: [docs/designs/issue-368-ci-issue-tracker.md](designs/issue-368-ci-issue-tracker.md)。
  - `.github/workflows/ci-issue-tracker-reconcile.yml`（Issue #368 通知 gap 対策の第二入口）は `schedule: "23 */6 * * *"`（UTC・6 時間間隔）+ `workflow_dispatch`（入力なし）で同一判定器を `tracker.mjs --reconcile` で呼ぶ。`GITHUB_TOKEN` dispatch の bot `ci` 完了は `workflow_run` event を発火させない（anti-recursion）ため、event 入口に届かない失敗・回復を権威 run 履歴 + marker 状態だけから reconcile する。`TRACKER_EVENT_PATH`/`GITHUB_EVENT_PATH` は一切読まず、`--event` との同時指定は usage error（mode 分離は `parseTrackerArgs` が強制）。job `reconcile` は `if: github.ref_name == 'main'` + checkout を `github.event.repository.default_branch` に pin（非 default ref での dispatch は no-op skip・tracker コードは常に mainline）。権限・concurrency group `ci-issue-tracker-<repo>` は event 入口と同一（workflow 横断で直列化・pending 置換は冪等性で回復）。public repo の ~60 日無活動による schedule auto-disable の blast radius を event 入口から分離するため cron はこの別ファイルに閉じ込める（ADR-vJvyZNtrHi2xnycJxbnSPv）。設計: [docs/designs/issue-368-tracker-reconcile.md](designs/issue-368-tracker-reconcile.md)。

## Consumer 影響分類の運用（Issue #219）

公開 API / feature / behavior / dependency / CI 基盤の変更 PR は本文の Consumer 影響欄で Synvelis・AudioLens を独立して `impacted` / `no impact` / `unknown` に分類する。`unknown` 残置は互換性未確認であり、merge 前にレビュアーが分類欄の記入と `unknown` 解消先リンクを確認する（required check 化していないため human gate）。記入有無・`unknown` 解消先・分類内容の妥当性の確認は全てレビュアーが担う（機械検査 lane は Issue #366 Stage 1 で撤去）。PR 本文の記入形式は `.github/PULL_REQUEST_TEMPLATE.md` が正本。
