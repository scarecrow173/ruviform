# GUI・GPUI・dock・テスト基盤の検証記録

本書は、UI ランタイム・GPUI ドライバ・dock・UI テスト基盤について行われた検証と実機実行の結果を記録する。記録の対象は、後に削除された過去の実装記録から抽出したものであり、本書はそれらの記録に依存せず単独で読めるように構成している。各記述には出典の Issue 番号を付記し、観測された事実と、その事実に対する分類・判断を区別して記す。実機検証は特に断りのない限り Windows 11 の対話 desktop session 上で行われた。

## headless 契約テストと dock の end-to-end 検証

実 OS を使わず window・job の不変条件を検証するため、`UiRuntime` と `FakeDriver` を本番 consumer 配線で合成する in-process 結合テストが追加された (Issue #243)。未被覆だった不変条件 — cancel scoping vs unrouted・orphan job terminal routing・stale id cleanup・stale inbound drop — を固定する 4 テストを実装し、job worker thread の timing 依存は deadline 付き bounded drain で吸収した。`mise run fmt-check`/`check`/`lint`/`test ruviform-ui-test` は全て exit 0、`cargo test --test window_job_headless` は 4 tests/0 failed で、origin/main merge（71445679→3d981b75）後の merged tree でも同一コマンドを再実行して pass を再確認した (Issue #243)。

dock の end-to-end は、fake host を使う `tests/dock.rs` で検証された (Issue #182)。detach（menu-move one-shot と begin+webview-ready+commit の両経路）から reattach までで論理 View ID と `MoveCommitted` handoff（consumer 側 view state を実演）が保持されることを確認し、create_window 失敗・Ready 未到達時の abort・commit 時の dest Destroyed rollback・close 3 ポリシー・snapshot save/restore も同じテストで検証した。`cargo test -p ruviform-ui dock` は persistence テスト（roundtrip・schema/構造/重複の reject・off-screen/missing-monitor 補正・dirty tree normalize）込みで pass し、`check-ui-webview`/`lint-ui-webview`/`test-ui-webview` も `position` 配線を含めて pass だった (Issue #182)。残課題として、`WindowConfig.width/height` は logical、snapshot 側は physical px であり、consumer が scale_factor 換算する責務を持つ（混合単位は snapshot 内で完結する設計）(Issue #182)。

複数 window の consumer 配線例として、`demo_multi.rs`（main+sub の 2 Window、handle_window/drain_jobs_routed→eval、last-window policy）が追加され、fmt-check/check/lint/test/test-ui-webview 系が全て pass した (Issue #181)。実機検証は実施範囲のみに留め、未検証 OS・異 DPI・モニター切断は `unverified` と明示した。consumer 影響は synvelis=impacted、audio-lens=no impact（単一 Window baseline 不変）と分類された (Issue #181)。

## driver 中立 lifecycle fixture と editor session の headless 検証

Fake と GPUI の両ドライバが同一の意味を持つことを headless で検証するため、driver 中立の共通 lifecycle fixture（`run_lifecycle` + `expected_trace()`）が追加された (Issue #386)。Fake Driver（workspace test）と GPUI Driver（`#[gpui::test]` + TestAppContext の 1 turn 毎 settle）は、2 Window・Dock 2-phase move/rollback・detach/reattach・close veto/defer/approve・無応答 close の既定・late receipt・id 非再利用・tear-down を含む同一 trace に一致した。検証の過程で、GPUI test platform の window は OS handle を持たず `window_handle()` が panic することが判明し、`capture_raw_parent` は `cfg(all(test, gpui-test))` で None を返す seam とした (Issue #386)。

この fixture では capability 宣言の不整合も検出された (Issue #386)。`GpuiDriver` は focus を Supported と宣言するが、`focus(_, false)` は gpui 0.2.2 の制約で `UiError::Unsupported` を返す。fixture が「Ok か Unsupported のどちらか（Host error ではない）」を要求するため、headless trace の一致は capability 宣言の正しさを保証しない。宣言の精緻化は後続 Issue 候補として deferred と記録された (Issue #386)。

plugin editor session の headless 検証は 3 系統の fixture で行われ、いずれも production コードへの差分なしで追加された (Issue #389)。第一に、`editor_session.rs` の EH-01..04 では、同じ visibility 要求は event/state を変えないことと、open→close・`notify_terminated(HostLost)`・refused open の各経路で実 `InProcessHost` の `lifecycle_state==Processing`・`process().status==Continue` が不変であることを固定し、49 tests pass だった。第二に、`editor_session_driver.rs`（FakeClock/ScriptedOps/FakeHostDriver）の SM-01..17 では、open/hide/show/resize/2相 reparent/close の全 lifecycle・detach/re-attach 相 abort の `Failed{PluginFailed}`/`Failed{LeaseInvalid}` rollback・generation recycle 後の stale drop/StaleRequest/double close 拒否・request timeout の `Failed{Timeout}`・preferred Unsupported 時の `begin_degrade` による Floating 明示 degrade（Degraded event のみ）・Terminated exactly-once・window close の Closed と instance destroy の Terminated の区別を検証し、18 tests pass だった。第三に、session hardening では SessionClock/deadline・OpenOutcome/`Degraded` event・GraphicsLost を additive に実装し SH-01..17 の 17 件を追加して計 45 tests pass だった (Issue #389)。実 wall-clock・実 plugin/GPU/OS での timeout/degrade/graphics-lost 発生は NotRun で、実時間依存テストの flaky 化を避けるため注入 clock で決定的に検証する方針が採られた (Issue #389)。

## TypeScript 側テスト基盤: browser spec・guitest・binding

browser 側は、gesture/keyboard-a11y/receipts-states/theme-lifecycle/viz/consumers/deps の各 spec を Playwright で実装し、全 spec pass・status done となった (Issue #310)。`deps.spec.ts` では Ruviform 全 package.json に react/solid/vue/svelte や実 DOM renderer の必須依存がなく、`@playwright/test` が browser-test のみであることを検査した。mise には check/build/test-ui-browser を追加し、CI の `ui-verify` job に ms-playwright cache→`npx playwright install chromium`（Linux は `--with-deps`）→`mise run test-ui-browser`→`test-results/` artifact upload（`if: always()`）の lane を配線した。`test-results/evidence.json` は env/revision/seed/pass-fail を含む (Issue #310)。

guitest 側では、設計上の fault matrix を TS 側に網羅実装し（terminal event 存在 assert 付き）、Rust 側にも fixture 駆動の conformance を配線した (Issue #311)。`ipc_conformance.rs` は fixture 読み込み→`parse_intent`/`Event::to_json`/`DataRegistry::read`/`UiRuntime::handle`/`handle_window` の照合と host scenario 再生・job backpressure/panic/cancel を行い、`scheme.rs` の既存テストは `rvf://data` wire 契約の fixture 駆動に拡張した（product コードは変更しない）。段階別の結果は次のとおりだった (Issue #311)。T1 では fail-closed ローダが全 15 fixture を parse し typecheck 0 errors（Windows 11 x64・Git Bash・Node 26.12.1）で、Rust 側 2 lane でも同一 fixture 群を読み込んだ。T2 では intents/events/data/binding-messages の全 fixture case が `expect` と一致し、`check-ui-guitest`/`test-ui-guitest` も lockfile 復元→typecheck→node --test まで一貫して PASS だった。T3 では 135 tests・0 fail（9 scenario×3 + fault-matrix 10 + recorder + wire + binding）で、同一 seed/clock/入力の 2 回実行 trace が bit 同一であること、genAckStorm/genAttachStorm の seeded fault でも terminal 保存・ghost command 非発生であることを oracle 照合で確認した。T4 では `ipc_conformance` 4 tests・`test-ui-webview` 8 tests・`test-ui-guitest` 135 tests・fmt-check/check/lint/workspace test が全て PASS（Rust 1.99.0・Node 26.12.1）だったが、`ui-verify` job への配線はローカル検証のみで GitHub Actions 実実行は未確認と記録された (Issue #311)。

binding 層の adopt-on-join（attach 前に作成された binding への join）は、test-spec 全ケースの恒久テストを先に追加して RED（10 fail）を確認し、実装後に `test-ui-binding` 99 pass の GREEN を記録した (Issue #377)。`check-ui-guitest`/`test-ui-guitest` は attach 前作成の既存 caller 経路に回帰なく 135 pass、showcase 73 pass で、review-protocol は blocker なしの ACCEPT だった (Issue #377)。

## Windows 実機検証: window lifecycle と OS 入力

window lifecycle の実機検証は、観測用 example `window_lifecycle_probe` を `wm-close.ps1`（`PostMessageW(WM_CLOSE)`）で駆動して行った (Issue #243)。既定モード `-Steps "veto,veto,veto,main"` で Veto/Defer/Approve・無応答時の既定 Approve・window 別 focus 遷移・`focus(w,false)`=Unsupported・id 非再利用（reborn=w3）・`destroy_window` の CloseRequested bypass を全て実測し `[probe] PASS` exit 0 を確認した。`--degenerate-create` の 0x0 `WindowSpec` は失敗せず Windows が最小サイズ 120x1 へ clamp して受理したため、invalid spec で生成失敗経路を誘発する検証は成立せず NotRun に分類した。`real_window_lifecycle`（`inspector,inspector,main`）と `minimal_window` も exit 0 で、fmt-check/check/lint-ui-gpui/test-ui-gpui は全て exit 0 だった (Issue #243)。

複数 window の実 OS smoke は `real_os_multiwindow_smoke` fixture（3 window・focus/keyboard/Dock/move/close/regenerate/job policy・OS oracle・cursor 復元）で行い、verdict=pass（17 checks）を 1 回実測した (Issue #243)。事後 run では SendInput が kernel driver に drop される環境退行を検出したため、cursor read-back oracle を強化（commanded point・cursor 実位置・hit-test・foreground を記録）して診断可能化し、capability matrix では Pass（実測済み）と NotRun（環境ブロック）を分類した。さらに最新 main（revision `4eea9115`）で `example-ui-gpui-real-os-multiwindow-smoke` を再実走して exit 0・verdict=pass を確認し、canonical verdict JSON を preflight 付き v2 schema で再生成して capability matrix の stale 行を実測に整合させた (Issue #243)。

clippy 対応 refactor 後の再実行では、`per_window_focus_real_click` 等 4 check が fail した (Issue #243)。commanded (1140,152) に対し cursor read-back は (586,1079)、foreground は無関係な `タスク マネージャー` だった。host-level 切り分けで、SendInput は受付を返すが注入イベントが一切効果を持たない system-wide ブロックと判定し、`mouse_event`/`keybd_event`/`SetCursorPos`/`WScript SendKeys`・Task Scheduler context・`vgk`/`vgc`/`vgtray` 停止・LG HUB/GameInput proxy kill・class filter・BlockInput・RDP・IL 差異を否定して、fixture/backend を変えず環境要因として記録に留めた（「SendInput 受理 ≠ カーソル到達」を fail として記録）(Issue #243)。

この環境退行の経験を受け、実機 lane には事前の注入可否判定（preflight）が設けられた (Issue #552)。`real_os_smoke`（Keyboard）・`real_os_pointer_smoke`（Pointer）・`real_os_multiwindow_smoke`（PointerAndKeyboard）の 3 件とも verdict pass・exit 0・`preflight.effective=true` を schema v2 で記録した。review-protocol で検出された空 scope の vacuous-true も修正済みで、preflight 不通の実環境再現は自然発生待ちとして、強制障害注入は行わない方針が記録された (Issue #552)。

実キー・pointer 注入の E2E は `os_input` モジュールと複数の lane で検証された (Issue #313)。`real_os_smoke` は `Ready`+`Focused(true)` 観測後に `SendInput(Tab,Right,Tab,Left)` を投入し、+step/−step commit intent が異なる control_id で両方観測されることを合格条件（Tab 巡回順は tab stop spec 順依存のため順序非依存）にして verdict=pass exit 0 を記録した。非 Windows は `unsupported`/exit 2 で「未実行」を「失敗」と偽らない設計だった (Issue #313)。`real_os_pointer_smoke` は Fader ドラッグ（Begin≈0.25/Commit≈0.75）と Seek クリック（≈0.8）を注入し、各 move 後に `GetCursorPos` read-back で commanded ±4px を確認した。これは「注入した」ではなく「カーソルが実際にそこへ行った」の証拠とするためである。2 回実行とも pass・intent 値 0.25/0.75/0.8 が一致し、起動時カーソル位置は終了時に復元した (Issue #313)。`test-ui-real-os-scenario` では、2 コントロール view を real window に mount し、実キー列（atomic Begin+Commit）→計測矩形上 pointer drag（non-atomic・gesture_id 一致）→click→`drain_intents` の IPC intent 検証→receipt `Applied` 観測→`capture_frame` 実ピクセル取得の全脚を検証して verdict `pass` を記録した。`RealOsPointerOrKeyboard` capability は `os_input::supported()`（Windows のみ）条件で claim し、os_* op は preflight read-back を family 単位で gate（session 内 cache）する構成とした (Issue #313)。

windowed uitest lane では、`RVF_WINDOWED_UITEST=1` gate の manual lane で全 11 op を実走 pass した (Issue #313)。hello（backend `gpui-windowed`・screenshot claim・input_injection/dom_access denied）・windows（real `Ready`）・fault.set・fault.window_crash（対象 window のみ `Destroyed`）・request_close（veto 維持→未応答 default-approve で destroy）・shutdown（`exited`・AUT は code 0）を記録し、screenshot は 320×240 rgba-raw 307200 bytes で整合した。env gate なしでは no-op skip で verdict を書かず、UI loop の死は `process::exit(3)` で fail-closed とした (Issue #313)。

この lane の初回実走では、800×600 級 RGBA→base64 の screenshot reply が stdio transport の frame cap `MAX_INTENT_BYTES`（1 MiB）を超過して `write_frame` が失敗し、serve が `DriverGone`→AUT 死亡→後続 op 全て `Disconnected`/`BrokenPipe` となることを発見した (Issue #313)。対処として adapter は encode 後に cap を pre-flight し、超過時は `service_error` で op のみ失敗させて channel を生かす構成とし、fixture は `width`/`height` で 320×240 window を capture 対象にして、pixel は常に実 capture・量だけを transport に合わせた。wire 側 chunked reply は closed op set 不変の制約で未着手と記録された (Issue #313)。

CI 上の照合では、対象 SHA `e93c438a` の Full CI run `43428172820`（conclusion=success）の job log から、`verify-{ubuntu,windows,macos}` の `test-full`・`ui-gpui-verify` 3 OS・`ui-gpui-offscreen-verify`（real_window 3/3 pass・`real_os_input_scenario` は Linux で `verdict=unsupported`）を lane/test 単位で照合し、capability matrix に 19 行を追加した (Issue #313)。併せて「adapter 未実装」の stale 行を、`RealOsGuiTest` が `real-scenario` feature で実装済みの実態に訂正した (Issue #313)。

実 window の close lifecycle は、`real_window_lifecycle.rs` の 2 test が実 Windows desktop で pass した (Issue #631)。`window_close_lifecycle` は、armed Veto→`CloseRequested` 観測・`Destroyed` なし、armed Defer→pending 維持→`respond_close(Approve)`→`Destroyed`+id 退役、unarmed→default Approve→`Destroyed`、sibling/sentinel 非干渉を各段 assert し、`window_dpi_geometry` は live `OsWindowGeometry` の安定性・`Resized` の物理 pixel 一致・破棄後の honest error を検証した。同一 lane の既存 `real_os_input_scenario` が初回 `NotRun — window w1 is not the focused window` で一度 fail したが、単独・lane 再実行で pass しており、並列 real-window test の OS focus 競合による環境 flake で本変更起因ではないと切り分けられた。teardown 時の `RefCell already borrowed`/`HRESULT 0x80070578` ログは、baseline の既存テストでも出る環境ノイズとして記録のみとした (Issue #631, Issue #313)。

WebView2 の実機検証では、`e2e_smoke` が milestones `["Created","ipc:ping","Ready","ipc:received"]`・exit 0 を記録した (Issue #431)。page の script は load 完了前に実行され result は backlog 経由で `Ready` 後に配送されるため、`Ready` が `ipc:ping` の後に来る観測が記録されている。`demo_app`/`demo_multi` の `WM_CLOSE` 経路も exit 0 で、終了時の `Chrome_WidgetWin_0 Error=1411` は既知ノイズだった (Issue #431)。`real_window_lifecycle` では、`inspector` への Defer（開いたまま）→Approve→`Destroyed`、`main` への Approve→`Destroyed`→loop 終了、Dock の 2-phase 遷移（v2 commit・v1 abort・v1 detach/reattach・`Destroyed` 後 `RelocateTo`）を各段で所有者検査して PASS exit 0 を確認した。陰性対照 `-Steps "inspector,main"`（inspector を 1 回しか閉じない）では trace 不一致で `[real] FAIL` exit 1 となり、照合が失敗を検出できることを確認した (Issue #431)。

## 実 window golden と story matrix

canonical story を実 window に mount した golden 検証は、`driver_class=real-os`・`capture=RealWindow`・実測 scale/backend の `golden_check` で `blocked/baseline_missing`→`pass/match`（compared=1,024,000・mismatched=0）を記録した (Issue #314)。idle/teardown の実 pixel capture（1280×800・`win32-printwindow`・sf1.0）と driver-lab/golden の JSONL・PNG を証拠として保存した。`dispatch_input` は semantic dispatch であり、pointer/keyboard 証拠を名乗らない境界が明記された (Issue #314)。`test-ui-real-scenario` lane は 2 story × 4 cell = 8 session が全て pass（2 tests passed・exit 0）で、driver-lab evidence 8 行全て `observed=pass`、16 PNG+8 meta.jsonl を記録した。対話 desktop session がない環境では全 cell が `environment_blocked` で fail する設計で、manual lane であり CI 対象外である (Issue #314)。story-keyed 実窓 capture（`golden_capture`・`--ignored`・desktop session）は 3 tests passed で、`--features gpui-test` では「window has no OS handle」の `unsupported` を返すことが確認された。OS handle の無い lane が pixel pass に昇格しない capability 分離の実測証拠である (Issue #314)。

## GPUI 採用 Gate と driver boundary

## DirectComposition による child HWND の画素非提示（Issue #532）

## 描画・状態管理の不具合と RED→GREEN 修正

外部 projection の描画反映では、「外部非ゼロ projection を idle で受けても `snapshot.observed` のみ更新され `display.normalized`（renderer 消費値）は初期値のまま」という反例を gpui/component_view test で RED 再現し、修復後に display/committed が authoritative 値へ更新される GREEN を全 lane で確認した (Issue #414)。driver-lab に `UI-DVR-09` required case を追加（required_cases 8→9）し、consumer 側 workaround は追加せず RF 所有境界で修復した (Issue #414)。

command の floor 管理では、fmt-check/check/lint/test と test-ui-* 系 12 lane（ruviform-ui unit 99 tests 含む）が全て exit 0 で、review-protocol で test-spec Rule「floor は control_id ごとに独立」に対応 test がない CONFIRMED P1 を検出し、`projection_floors_are_independent_per_control` を追加して解消した (Issue #410)。`update` 経路は binding 存続のため floor の clear/非 clear は観測不能（P3・記録のみ）と判定し、全件 LiveExpect 時に command_index が bound を超えて yield する点（binding 数×上限で有界）と非 receipt command の配送喪失が timeout なしで残る点は既存契約の範囲として記録された (Issue #410)。

review で検出された不具合として、range-selector は per-edge control id（`<id>-lo`/`-hi`）が single `<id>` binding の filter に捨てられ silent unwire になっていた問題を、edge bindings+targets+`bindRangeElement` reflect path に修正し、`range-lo` commit の gateway 到達を regression test で assert した (Issue #263)。showcase の receipt drain が microtask flush 前に `received` を splice して commit が 1 gesture 遅れ・最後の gesture が timeout `invalid` になる race も `flushWith` 同期 mount で修正し、theme parity の vacuous assertion への非空 assert 追加・a11y coverage 拡張・stale reply 配線も実施した (Issue #263)。

WebGL2 移行では 3 件の blocking finding を修正した (Issue #260)。第一に、GL hatch は rect をはみ出す segment を意図的に描くため Canvas2D の `ctx.clip` に依存していたが、WebGL2 には per-op scissor がなく meter gap-hatch が canvas 全体に streak したため、`pushClip`/`popClip` を追加した。第二に、`getContext("webgl2")` 成功後は同 canvas の `getContext("2d")` が永久に null になる context pinning のため fallback と `webglcontextlost` recovery が dead end となっており、`replacePlotCanvas` で新規 canvas node に差替えてから Canvas2D retry する方式へ修正した（context-pinning fake canvas で regression test）。第三に、superseded な in-flight query が cache-hit/empty-span の early return で abort 前に走り stale data が着地する問題を、`++querySeq`+abort を invalidate 先頭へ移動して解消した (Issue #260)。

layout の高さ計算では、Fader/Knob の `h_full` が残り高を独占する問題を `grow`+`min_h` slot へ修正した (Issue #478)。旧実装への先行実行で RED（Fader=936px・Waveform=120px・grow slot 合計 1038.5px vs 期待 1032px）を確認してから、gpui-test 3 件の追加で GREEN を記録し、UI lane は全 pass だった。`component_showcase` 実窓では Fader≈299px の body 残り充足と drag gesture の Begin→Preview×13→Commit intent 列を観測した (Issue #478)。canvas 寸法では、Seek canvas が 0px×24px だった問題を `size_full()` 付与で修正し、回帰テストを先に追加して RED（0px×24px で失敗）を確認後 GREEN（test-ui-gpui 54 件）とした (Issue #450)。さらに全 paint canvas の prepaint bounds を記録する監査を導入し、修正前に Waveform/Meter/Spectrogram が 1920×0・TimeAxis が 1920×18 である失敗を検出してから、viz slot を flex column・flex_grow・min_h(120)・canvas `size_full` に統一（TimeAxis は flex_shrink_0）して修正した。修正後は test-ui-gpui 57 件 pass で、`component_showcase` の修正前後撮影で Waveform 空白→bins 表示を確認した (Issue #453)。

state 管理では、`RvfView::flush_events` で `Removed`/`Unmounted` op を受けたとき `tab_focus` の対応 entry を解放し、strip の FocusHandle が spec の存続期間を超えて残らないようにした (Issue #480)。解放検証テスト（Removed・kind-swap・Unmounted・sibling 保持・Updated 保持）を RED 3 fail→GREEN 3 pass で確認し、op が flush まで滞留する経路は production に存在しない（全 mutation path が同期 flush）ことも確認済みだった。`control_focus` の解放は範囲外として deferred と記録された (Issue #480)。

実窓での操作証拠は、Windows のフォーカス制約を避けるためフォーカス API ではなく OS 実ポインタ `mouse_event` で取得し、`component_showcase` 実窓で Ch 1→Ch 2→Ch 1 のタブ切替を確認した (Issue #451)。自動化 pointer テスト（TestAppContext）で同じ経路を検査し、実窓は補助証拠と明記する方針を採った (Issue #451)。レビュー運用では、協調・敵対・検証・判定の役割を分離したパスで review-protocol を実施し、確定した P2 欠陥 2 件（読み取り専用化後の選択残存・復元時の範囲外行）を修正して回帰テストを追加した (Issue #448)。webview driver に ViewSpec 描画経路がないため webview parity は NotRun で、別 Issue の対応を推奨と記録された (Issue #448)。

## paint 性能: O(n²) 回帰の計測と paint_layer 化

契約上限 payload の repaint は、headless `TestAppContext` の実 paint 経路（Scene 構築・`BoundsTree::insert` を含む）で計測した (Issue #461)。修正前値は Spectrogram 6.37s・Waveform 45.19s・Meter 13.06s・TimeAxis 906ms（debug build）だった。原因は gpui の `BoundsTree::insert`→`find_max_ordering` の走査構造にあり、4 painter の要素ごとの quad を `window.paint_layer` で囲む修正後は 53.3ms/27.3ms/11.5ms/806ms となった。budget 500ms（実測の約 10 倍・O(n²) 秒オーダーとの識別を優先）で `rvf_view_max_payload_canvas_repaint_budget` を回帰ゲートとして追加した。実機 paint 計測は NotRun だが、headless で全経路を通すため O(n²) 回帰は検知可能と判断された (Issue #461)。

残課題の TimeAxis label コストは、label `div`（最大 1,024 要素）を廃止し、canvas prepaint で `WindowTextSystem::shape_text` により shaping した label を共有 `paint_layer` 内で glyph 描画する方式へ変更して解消した (Issue #461)。診断計測では label 空で約 125ms・1,024 labelled で約 0.8〜1.7s・全 cull で約 262µs であり、per-line `paint_layer`→`BoundsTree::insert` が支配的と特定した。修正後は約 11ms となり、`time axis 1024 labelled ticks` ケースを budget テストへ追加した (Issue #461)。
