# CI レーン・ゲート・ツールチェーンの実行記録

この文書は、ruviform リポジトリの CI レーン構成、必須ゲート、ツールチェーン管理について行われた検証と実行の結果を記録する。各事実には由来する Issue 番号を付記し、実測値や観測された動作はそのまま記す。実施されなかった検証は Pass に含めず、NotRun または対象外として区別する。判定には `Pass`/`Fail`/`Unsupported`/`NotRun`/`Blocked` の語彙と「`NotRun` を `Pass` にしない」正直性ルールが使われており、後述する各 lane の証拠行もこの語彙に従う (Issue #127)。

## ローカル検証レーンと mise タスク

開発基盤の検証は、Windows x64・mise 2026.10.1・Rust 1.99.0 の環境で実施され、関連する全タスクが exit 0 で完了した (Issue #2)。

`cargo test --workspace` と `cargo build --workspace` はいずれも exit 0 で、`--profile ci` ビルドも exit 0 だった。成果物は `target/debug` と `target/ci` に分離して生成され、`git check-ignore` で `target/` が除外対象・`Cargo.lock` が非除外であることを確認した。`[profile.` 定義はルート `Cargo.toml` に 3 件（dev・ci・ci.package."*"）のみで重複なく、workspace 継承は edition・rust-version・license・lints の 4 行で確認した。`cargo check --workspace --all-targets`、`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets -- -D warnings`、および `CARGO_INCREMENTAL=0` 下の ci profile での check/test/clippy も全て exit 0 だった (Issue #2)。

mise タスクは新規 11 件を含め全て exit 0 で、`verify-ci` は fmt-check→check-ci→lint-ci→test-ci の順に実行され、後半 3 タスクが `ci` profile で Finished し、テストバイナリが `target/ci/deps/` 配下に生成された。`CARGO_INCREMENTAL` は mise.toml に 5 行明示され、`prek run --all-files` は全フック Passed、`.pre-commit-config.yaml` と `mise.lock` に差分はなかった (Issue #2)。

リポジトリ反映の検証では、`cargo metadata` で ruviform-core の publish が `null` から `[]` に変化し、`mise run fmt-check`/`check`/`lint`/`test` が doctest 1 件を含め全パス、文書監査が 40 ファイルで findings 0 だった。edition・rust-version・license の値、mise.toml、ci.yml、Cargo.lock に変更がなく、新規クレートや LICENSE ファイルの作成もないことを確認した (Issue #1)。

## ツールチェーン解決と mise.lock の整合

`mise install --locked` は当初 pipx 経由ツール 2 件の欠陥で exit 1 を返した。`pipx:apm-cli` は `uvx_args` が dependency locking 非対応、`pipx:serena-agent` は dep graph 欠落が原因だった。`uvx_args` の除去（apm-cli 0.33.0 は PyPI final release で `--prerelease allow` 不要）、GitHub shorthand spec への変更、`uv` 0.12 更新、`.mise/locks/` の dep-graph コミットにより、リポジトリ管理の全 7 ツールが `mise.lock` から解決することを実機で再検証した（`apm --version`→0.33.0、`serena --version`→1.7.0）。残る exit 1 は global mise config 由来の、リポジトリ lockfile 管理外ツールだけの環境 caveat と記録された (Issue #2)。

`apm install --frozen` は apm-cli 0.33.0 で実装済みで、`apm install --help` に `--frozen`（apm.yml と apm.lock.yaml の非同期時に拒否する CI-safe フラグ）の存在を確認した。main リポジトリ（exit 0・9 deps）とクリーン worktree（exit 0・31 deps + 2 MCP servers）の双方で成功し、`git diff --exit-code -- apm.lock.yaml` も exit 0 で冪等だった (Issue #2)。

クリーン `git worktree` での V-1〜V-11 検証マトリクスは全件 pass で、`apm install --frozen`・setup 3 コマンド・`verify-ci`（`--profile ci`・`CARGO_INCREMENTAL=0`）・`test` が exit 0、`target/ci` と `target/debug` の分離生成、`git status --ignored` が意図した生成物のみを示すこと、ソース差分ゼロを実測した。V-8（CI ディスク計測）は静的確認 pass とし、実ディスパッチは default branch マージ後のため未実施として区別した (Issue #2)。

## MSRV 検証と toolchain 別実測

MSRV 検証の呼出形は `rustup run <version> ... --lib --locked` に統一された。`cargo +<version>` は rustup proxy 前提のため採用せず、dev-dep のバージョンは caret 指定とし、追跡済み `Cargo.lock` を再現性の錨とする方針が記録された (Issue #19)。

MSRV 1.89 への引上げは toolchain 実測で確認された。`rustup toolchain install 1.89` の後、`cargo +1.89 check --workspace --all-targets` が let-chains を使う bench/test ターゲットを含めて成功し、`cargo +1.89 check -p ruviform-math --lib` でも退行がなかった。1.85 時点の「`--lib` のみ成立」という既知制限は解消した。引上げに伴い clippy が 1.87〜1.88 安定化 API（as_chunks/as_chunks_mut/is_multiple_of/let-chains の collapsible_if）を提案するようになり、`cargo clippy --fix` と手動補完で計 16 箇所に機械的修正を適用した後、pin toolchain 側の `mise run fmt-check`/`check`/`lint`/`test`/`test-rt`/`bench-smoke` と `prek run --all-files` が全パスした (Issue #52)。

Rust 1.89.0 の clippy では別途 5 系統の失敗を実測した。内訳は `float_cmp` 272 箇所・`similar_names` 35 箇所・`unfulfilled_lint_expectations` 11 箇所・`must_use_candidate` 1 箇所・`range_plus_one` 2 箇所で、pin toolchain（clippy 1.99.0）では全て不発火だった。`unfulfilled_lint_expectations` は 1.89 で expect 属性の期待が充足されない不整合だった。修復後は `cargo +1.89.0 clippy --workspace --all-targets -- -D warnings -A clippy::float_cmp -A clippy::similar_names` が exit 0 となり、文書化した除外 lint のみが残存した。`ruviform-numeric` の 105 テスト合格で `invert` 書換の動作等価性も担保した (Issue #223)。

GUI guard lane の MSRV 検証では、`mise run test-ui-test-msrv`（rust@1.89.0）が当初 `cargo-platform@0.3.3 requires rustc 1.91` で exit 101 を返し（RED）、修正後は Rust 1.89.0 で全 76 テストが pass した（GREEN・内訳は driver_boundary 10・driver_contract 5・e2e_process 15・fake_driver 14・headless_contract 32 等）。merge 後（origin/main 68bb8710 取込）は Cargo.lock union（削除行 0）で 88 テスト pass となり、fmt-check/check/lint/check-ui-driver-boundary/test-ui-driver-contract/test-ui-component-view/test-ofx-msrv も全パスだった。なお merge 後の workspace `mise run test` で `ruviform-plugin-host` の l1_proxy_e2e `wedged_child_write_converges_and_teardown_is_bounded` が並行負荷時に 1 度だけ spawn timeout したが、既知の flaky として記録済みのもので本変更と無関係と判断し、単独再実行で当該 suite 184/184 pass を確認した。macOS/Linux 実機は NotRun（Windows 11 x64 のみ実測）と記録された (Issue #411)。

## bench レーンとプロファイル分離

bench スモークは `cargo bench -p ruviform-math -- --test` を実行する `bench-smoke` タスクとして追加され、ci.yml の `bench` ジョブは `mise run bench-smoke` を呼ぶ構成とされた（CI スモーク分離方針）(Issue #19)。

dev-dep 導入前後のコールド計測（2026-10-20・Windows x64・rustc 1.99.0）では、`cargo clean` 直後の `cargo check --workspace --all-targets` が導入前 0.60s（cargo 報告）/ 0.81s（wall）に対し、導入後は同条件で 30.14s / 30.38s だった (Issue #19)。

後続の変更で `bench-smoke` の対象は bench target を持つ 5 crate（ruviform-math・ruviform-rt・ruviform-viz・ruviform-numeric・ruviform-io-e2e）の `-p` 列挙へ拡張され、bench profile 破損（Issue #646 型）を CI lane で恒久的に検出できる状態にした。`--workspace` 化は bench target を持たない crate の lib test target まで暗黙に広げるため不採用とした。追加対象の `corr`（ruviform-numeric、Issue #265 由来）と `io_composition`（ruviform-io-e2e）の bench target の実在を確認したうえで、`mise run bench-smoke` が exit 0（5 bench target の実行行を確認）、`cargo bench --workspace --no-run` も exit 0、`mise run fmt-check` と `prek run --all-files` も exit 0 だった。CI `bench` job は既存の `mise run bench-smoke` 経路のため workflow 変更は不要で、`*-msrv`・`*-full`・3 OS 横断はこの変更の明示対象外（Daily Full CI 委譲・NotRun）とされた (Issue #650)。

## SIMD PoC 計測と dispatch コスト

DSP/SIMD PoC の採否判定は `mise run bench` の全量計測に基づく。単一プロセスでの全量実行は多数の並行エージェント稼働下で Windows コミット上限に逼迫し 2 回 abort したため、カーネル別 8 分割（各約 25〜27 分）で 2 run × 756 ケースを完走させた。結果は `fearless_avx2` が dot 7.9–8.3 倍・fir 3.6–5.8 倍・biquad 約 2.8 倍・fade 4.1–6.7 倍、`pulp_v3` が dot 8.1–8.9 倍だった。`multiversion` は dot 約 1.0 倍・fir 0.69–0.73 倍で不採用、`sine` は全実装でほぼ 1.00 倍であり、SIMD が適用されない領域では高速化が起きないという反証として記録された。この計測を根拠に、カーネル別適用とサイズ応答ルーティングの二層構造を採用し、MSRV 1.85 を維持する（dev-dep への封じ込め）ことが ADR で確定した (Issue #19)。

同じ計測で、`fearless_dispatched` の elementwise 小バッファがスカラーに劣後する事象が観測された（add/64=0.58 倍、@1024 で add 0.62 倍・scale 0.66 倍 vs 強制 avx2）。per-call dispatch コストかノイズかはこの時点では未分離で、約 350 プロセス並行稼働下の計測には run 間差 |Δ| p90=25.7% のノイズが含まれていた (Issue #19)。

低負荷条件での再計測が後続として行われた。計測前に環境負荷（OS CPU 9–20%・プロセス約 390・実行中エージェントは本セッションのみ）を記録し、dispatch_probe と add/scale/clamp_unit/fade のフィルタ実行を 3 run（各 261 ケース完走・クラッシュなし）で計測した。プローブ値は dispatch_noop 1.29ns（3 run で ±0.005ns）・level_new/token_avx2 約 0.43ns で、run 間分散 |Δ%| は p50 4.0%・p90 30.7%・p99 91.9% だった。前回（p50 1.8%・p90 25.7%・p99 237.7%）より極端値は改善したが分散は依然有意で、per-call 素コストは十分小さいものの run 間変動が支配的と分離できたため、結論は構造的分離で出すと記録された (Issue #56)。

SIMD dispatch 実装の検証では、`SimdToken::detect()` が開発機で `"avx2"` を返し、forced 各 token で全 8 カーネル・全サイズ帯がスカラー参照と契約適合した。`tests/simd_equiv.rs` の本番列（prod_detected/avx2/sse4_2/fallback/neon probe-gated）がグリーン、`rt_dsp_kernels_no_alloc`（assert_no_alloc）が合格し、公開 API に fearless_simd 型が露出しないことを cargo doc シグネチャで確認した (Issue #53)。

RT 関連の規約監査は Phase F の総合検証として実施された。4 公開 enum の `#[non_exhaustive]`・両クレート計 64 箇所の `**RT contract:**` ラベル・29 件の `rt_*` 単体テスト選択（exec 0 件）・test-scoped allocator 以外の unsafe ゼロ・外部型非露出を全て確認し、`mise run test` は単体 115 + doctest 97 = 212 件合格、`test-rt`/`bench`/`prek`/`cargo metadata`（全 6 パッケージ publish=[]・rtrb/arc-swap/audio_thread_priority の依存を記録）も全パスした (Issue #21)。

## CI ワークフローの trigger と required context

`ci.yml` は `workflow_dispatch` 専用化され、`on:` から `pull_request`/`push` を除去した。`inputs.expected_sha` の宣言は name/type/required/description 一切不変で維持し（Daily dispatch 契約）、concurrency を `ci-<run_id>`・`cancel-in-progress:false` に簡素化した。workflow 横断の trigger 不存在は新設の contract test（`ci/daily/tests/ci-yml-contract.test.mjs`）で固定し、全 `.github/workflows/*.yml` に `pull_request:`/`pull_request_target:`/`push:` trigger が 0 件、`ci.yml` の trigger 集合が厳密に `{workflow_dispatch}` + `expected_sha:`、`ci-issue-tracker.yml` に `workflow_run:` が存在することを Node stdlib で scan した。撤去前の状態で失敗することを確かめてから適用する RED→GREEN の順で記録し、この test は `test-ci-daily` 経由で自動包含される（新 mise task は作らない）。この変更の前提として、`main-checkstatus` disabled（Ruleset 26547674）・`main-protect` active（26529830）・Classic 404・reconcile の main 成功 run 42178261480・`ci-issue-tracker-reconcile` workflow active（id 409034138）を実測済みとし、actionlint clean・lane/job/permissions 不変・他 4 workflow byte-identical も確認した (Issue #326)。

PR concurrency では `ci.yml` と `consumer-impact-check.yml` に workflow-level `concurrency` block を追加し、`pull_request` では group を `${{ github.workflow }}-refs/pull/<N>/merge` で `cancel-in-progress: true`、それ以外の event では `${{ github.workflow }}-<run_id>` で cancel 無効とした。cancelled な check run は required check の合格条件（success/skipped）を満たさないため偽装経路はなく、cancel 方向は fail-safe（古い revision の check が欠けて merge 不可になる方向で誤マージは起きない）と評価された。既知の edge として、古い run の手動 re-run が同 group に再入して最新 run を cancel し得る点が記録され、復旧は最新 run の再実行または再 push とした。静的検証（actionlint 全 pass・job 名/job 数/trigger/permissions/step 非変更）は完了したが、同一 PR 連続 push で旧 run が cancel される実測は coordinator 引き継ぎで NotRun とされた (Issue #328)。

## CI 性能計測と runner 逼迫

3 リポジトリの CI baseline は `ci/metrics/collect-ci-metrics.mjs`（Node 標準のみ・`gh api` read-only）で実測された。代表 run は ruviform 41780346388（wall 318s・critical path 313s = ui-verify windows）・audio-lens 41770611162（wall 326s・cp 319s = verify windows）・synvelis 41782019309（wall 228s・cp 221s）で、Issue 本文の観察値 313/313/218s を正確に再現した。統計は ruviform n=14 で wall p50=302s・p95=458s、synvelis n=10 で p50=242s・p95=301s、audio-lens n=2 は計測契約に従い統計値を出さず観察値のみ報告した（n<10 で統計値を出さない fail-closed ルール）。required contexts は ruviform のみ branch protection strict=true で 12 件有効、audio-lens/synvelis は保護未設定（404）として区別記録した。実測で得た 7569 record の raw JSONL はデータとして保存された。計測契約は指標分離（wall/queue/job_wait/job_exec/exec_span/critical_path/runner_total）・lane 分類・Cold/Warm 区別・比較条件の固定値からなり、分類不能は `other` で名列挙し、`--logs-run` は rate limit の支配項になるため opt-in とした (Issue #327)。

計測の主要観察は 3 点ある。第一に、3 リポジトリとも critical path は `verify`/`ui-verify` の windows-latest job で、wall time がほぼ最長 job に一致し、単一 lane の短縮が wall に直結する構造だった。第二に、mise tool cache は全 job・全リポジトリで系統的に miss し、job あたり 13–23s の固定コストになっていた。第三に、rust lane（compile/check/clippy/test）が step 時間の支配項で（ruviform 1245s・audio-lens 785s・synvelis 534s）、audio-lens の cargo cache は lockfile hash 直結で頻繁に cold 化していた。集約 gate（audio-lens summary・synvelis evidence）は wait が critical path 長に等しいが exec は約 3s、consumer-verify の consumer leg は直近で失敗しがちと観測された (Issue #327)。

macOS runner の逼迫は required lane の実害として観測された。Before 計測（15 run）で wall p50 307s・p95 497s・代表 run critical path 235s・runner_total 1474s、ある push run では queued 2279s 超を観測した。さらに該当 PR 自身の CI run 41863215849 で macOS legs が queue 約 17–25 分の後 3 連続 cancel（step 未実行・runner 割当前に cancel）され、他 10 job は全緑だったため、macOS 逼迫が required lane に局所化していることが示された。これが macOS lane 物理分離の動機となった live 証拠で、After メトリクスは未実測（merge 後の選択実行 run で収集予定）と記録された (Issue #346)。

## コンパイルキャッシュと依存セットアップの最適化

sccache は `mozilla-actions/sccache-action` を immutable commit SHA `fc920bf0ec8de6ee65d409111f7ec508035751ba`（v0.0.11）で pin し、sccache v0.19.0 を GHA cache backend で verify/ui-verify の 3 OS に導入した。`RUSTC_WRAPPER=sccache` と `SCCACHE_GHA_VERSION=ruviform-v1-<RUNNER_OS>`（OS 名前空間）は `actions/github-script` 経由で `GITHUB_ENV` へ export した（`ACTIONS_RUNTIME_TOKEN`/`ACTIONS_RESULTS_URL` は JS action コンテキストでのみ確実に参照できるため）。kill switch は repo variable `CI_SCCACHE_DISABLE=1` で workflow YAML 変更不要とした (Issue #329)。

cold run 41816075282 では 3 OS の verify/ui-verify が green・12 required checks 全 success だったが、cache write error が 36–100% 発生した（ui-verify windows は 100%）。原因は GHA cache backend の rate limit と 6 job 並列の書込競合で、sccache は write error でも compile を継続する fail-open のため全緑を維持した。warm run 41816923217 では verify lane の hit rate が ubuntu 47.32%・windows 62.50%・macos 51.59%、job 時間は ubuntu -51s・windows -78s・macos -32s（10–30% 削減）で、ui-verify は ubuntu 29.67%・windows 0.95%（cold write 全滅の影響）だった。cache errors/read errors は全 job で 0、kill switch では 4 sccache step 全て skipped・job success を実証した (Issue #329)。

ローカル補助実験（Windows 11・`CARGO_INCREMENTAL=0`・local cache backend）では 3 点を確認した。cache 全 entry を破損させると誤結果を返さず re-compile に fallback し（stats: cache errors=12・compilations=14・hits=0）、`cargo update --precise` で lock hash が変わると miss して再 compile し、`RUSTC_WRAPPER` 未設定では通常の rustc compile/test が正常に動作した。別 target dir でも同一 key で hit し、cargo fingerprint 非依存であることも確認した (Issue #329)。

## impact 分類から Full CI への移行

impact-based CI はまず Shadow Mode で導入された。`ci/impact/`（stdlib-only Node `.mjs`）に classifier + map + gate を実装し、分類は `cargo metadata` の workspace 逆依存伝播・`rt_` 保持 crate scan・mise task `-p` 引数・`ui/*` DAG・full-fallback 規則で機械導出する。曖昧・分類不能・共通設定変更は Full CI に倒し（部分 lane 集合の誤判定は偽陰性源のため lane 推論を試みない）、diff は `git fetch --depth=1 origin $BASE` 後の two-dot tree diff で merge-base 不要として shallow clone と両立させた。lane job の `if:` は一切変更せず既存 12 required contexts を維持したまま、`impact`（分類 + decision artifact）と `ci-gate`（`if: always()` で needs 全結果を job 粒度で判定・gate-report artifact）を追加した。`pull_request` types には `ready_for_review`/`edited` を追加した。`edited` で title 編集でも再実行されるが、concurrency group が前 run を cancel するため実害がなく、base retarget での stale 期待集合を防ぐ利点が上回ると判断した。`ci-gate` は matrix leg ではなく job 粒度の `needs` result を判定し、per-OS 内訳は各 leg 自身の check run が持つため checks API への権限追加は避けた (Issue #333)。

Shadow Mode の観測は PR #345 run 41835836190 で行われた。`impact-classify` 18s pass・decision=`full`（ci-config+shared-config が fallback 規則どおり発火）・`ci-gate` 10s pass・6 lane 全 Pass・既存 12 contexts 全 pass で、gate-report は `verdict=pass`・`classificationOk=true`・6 lane 全 `expected=true/result=success/verdict=Pass` だった。追加分は約 28s で critical path 外（verify windows 4m4s が最長）だった。expected 集合 = 実行集合（full 判定）のため偽陰性検出器はこの run では未発動で、部分集合 expected の実測は未観測と記録された (Issue #333)。

Full CI Stage1 では `ci.yml` を全 lane 常時実行に変換し、`ci-summary` fail-closed 集約・`io-structured-verify` lane・`expected_sha` 契約を導入した。`ci/summary/summary.mjs` は needs JSON 評価・verdict・Job Summary・report JSON を出力し、verdict 行列は all-success→pass / failure・cancelled・skipped・missing・unknown→fail、expected_sha は空=照合なし・一致・不一致、NEEDS_JSON の parse 失敗→fail とした。`*-macos` 3 job を無条件化し、`macos-report`/`ci-gate` を `ci-summary`（needs 11 件・`if: always()`）へ置換した。`verify`/`l1-real-verify`/`ui-verify` の job id・matrix os 配列・`name:` は編集せず required context 不変を維持し、選択実行専用だった `ci/impact/` と `consumer-impact-check.yml` は削除した（分類要件は PR template + human gate で代替）(Issue #366)。

macOS GPUI lane は matrix ではなく物理分離 job `ui-gpui-verify-macos` とした。matrix leg は `needs.<job>.result` が 1 値に集約され失敗 OS を判別できないためである。`build-full` は接続せず、`test-full`（cargo test --workspace）が実行 bin の Build/Link を実質包含し、唯一の空白 `windowed_test_app` は `test-ui-gpui` の `--features "gpui-test uitest"` 拡張で塞いだ。初回 Full CI run 43421898733 で `ui-gpui-verify-macos` が `lint-ui-gpui` の `clippy::doc_markdown`（capture.rs:883 の `NSView` バックティック欠落）で失敗した。`#[cfg(not(any(windows, target_os = "linux")))]` の macOS 専用 module 内のため Linux/Windows lane では一度も lint されていなかった潜在欠陥を新 lane が fail-closed で検出した形で、crate 全体の cfg 監査で macOS 固有 compile surface はこの 1 module のみと確認し、`#[allow]` 抑制ではなく comment-only 修正を適用した。2 回目 run 43424042262 は全 20 job success・ci-summary verdict PASS で、walltime は 8m29s→13m44s（+5m15s）、runner 時間合計は約 46min→約 62min（+約 16min）だった。増分の内訳は新規 macOS lane 8m35s と、uitest 追加による feature 組合せ変更で GPUI 系 3 lane の compile が増えた分（初回は sccache key が cold）と記録された (Issue #598)。

## daily scheduler と CI failure tracker

daily scheduler は `daily-ci.yml` + `ci/daily/decide.mjs` で構成され、「現在 main SHA に有効な Full CI がなければ `ci.yml` を `workflow_dispatch` で起動する」判定を行う。判定行列（skip-verified / suppress-in-flight / hold-unknown / budget-exhausted / dispatch）、attemptsOn 厳格性、auto dispatch 計上（bot actor のみ）、latestVerified、dispatch 確認（confirmed/landed-mismatch/unconfirmed）、main-moved 再照合、error/exit code、report+summary 形状を `node --test` で検証した。schedule は UTC `"17 21 * * *"`（06:17 JST）で、workflow は `schedule` + `workflow_dispatch`（`dry_run` 入力）・`permissions: {}` → job `contents: read`/`actions: write`・直列非 cancel の concurrency・`test-ci-daily` 先行・report artifact の構成とした (Issue #367)。

CI failure Issue tracker は `ci/tracker/tracker.mjs` を stdlib-only Node `.mjs` として実装し、`workflow_run` 完了ペイロードを scope（repo × workflow `ci` × branch `main` × event ∈ {push, workflow_dispatch}）で分類し、注入 client 経由で GitHub Issue 一覧・job メタ・compare を取得して create/update/close-recovered/close-duplicate/noop の action plan を組み立てる。63 件の mock-client contract test（初版 34→45→56→63 件と拡張）で検証され、`mise run test-ci-tracker` 63/63 pass だった。

実装中に複数の post-review hardening が行われた。判定順序は `(run.id, run_attempt)` とし（run.id 単独比較だと失敗 run の成功 rerun が stale 扱いで永久に close 不能になる bug を発見）、異 run 間は `updated_at` 中心の ordering に強化した（同一時刻・欠損は `ambiguous` として close/成功判定から外す）。run-history reconciliation は concurrency pending 置き換え・通知逆転・完了通知の喪失/遅延に対応する。marker 参照の suppress は `(runId, attempt)` 単位に修正した（run id 単位だと「失敗 a1 記録済み + 一覧に同 id 成功 a2」で記録済み failure が消え auto-close 不能になることを reviewer mock replay が実証）。履歴 record は `classifyHistoryRecord` で out/in/unknown の 3 分類とし（in・非 completed は `pending` 証拠、unknown は close と resolved-suppression を両方止める）、`status=null` を completed と仮定する経路を排除し、event payload 側は `status === "completed"`・`run_attempt` 存在を必須化した (Issue #368)。

marker JSON の injection 対策は二重化され、job 名を入力境界で sanitize し（`-->` を含む job 名で HTML comment breakout できる経路を発見）、marker JSON 内の `<`/`>` を unicode escape した。tracker の運用契約と再利用 contract は `ci/tracker/README.md` に、`test-ci-tracker` タスクと workflow の所在は `docs/development-environment.md` に記録された (Issue #368)。

`ci-issue-tracker.yml` は `workflow_run {workflows:[ci], types:[completed], branches:[main]}` のみで起動し、`track` job には最小権限（contents:read / actions:read / issues:write）を限定付与、repo 単位 concurrency（cancel-in-progress:false）で直列化した。checkout するのは default branch の自分自身で（`workflow_run` は default branch の workflow ファイルで実行されるため失敗 run 側のコードには触れない）、self-test を API 呼出し前に置く（`test-ci-tracker` が失敗したら GitHub API に一切触れず job が落ちる順序）。`GITHUB_TOKEN` dispatch の完了が `workflow_run` を発火させない anti-recursion gap は、event 非依存の `--reconcile` モード（同一判定器・権威履歴 + marker のみ）と別 workflow `ci-issue-tracker-reconcile.yml` の `schedule`/`workflow_dispatch` 入口で埋めた。`--reconcile` 経路では `TRACKER_EVENT_PATH`/`GITHUB_EVENT_PATH` の ambient env を無視する規則を test で pin し（ambient env の存在を error にしない規則を誤って厳しくしない）、`parseTrackerArgs` を分離 export して `run({reconcile})` が `classified={kind:"reconcile"}`・report/summary に `mode` を付与する構成とした。実 cron・実 Issue・実 dispatch は行わず、全て mock client + actionlint + `git diff` の offline 検証とし、実 cron 受入は merge 後の別工程とされた (Issue #368)。

文書グラフでは、doc-driven-dev-graph の router が Issue #243・#313・#410 系文書を含む既存の repository-wide broken relation に対し `blocked`/`focus-required` を返す状態が確認された。関連 slice で追加された新規文書は索引・relations とも整合しており、既存 graph 欠陥は各タスクの範囲外として未修復のまま記録された (Issue #243)。

## consumer-verify の lane 構成と証拠契約

consumer-verify は `workflow_dispatch` 専用の情報 lane（preflight + verify-audiolens + verify-synvelis + summary）で、credential 未設定時は `not run` 出力＋全 lane not run で workflow を失敗として正直に示す（証拠ゼロを緑にしない）契約とした。`CROSS_REPO_DEPLOY_KEY` 未設定かつ匿名 HTTPS read 可能な場合は `anonymous` mode で lane を実行し、`deploy_key` mode（SSH・known_hosts pin・`url.insteadOf`・cleanup）は private 前提の canonical 経路として維持した。access mode の probe は consumer 単位で独立とした (Issue #219)。

manifest の rev 書換は「`rev` pin 置換・`branch` 追従除去・`rev` 未指定への注入」を同一ルールで `rev = "$RUVIFORM_REV"` へ正規化する sed に両 lane で統一し、書換 no-op は単一 SHA guard の 0 行検出で必ず fail とした（silent pass にしない）。この sed は 1 行 inline-table 形態を前提とし、git 指定を multi-line table で書く consumer への変更が入ると書換 no-op となるが、単一 SHA guard が必ず fail する設計でカバーした。review で確定した workflow の落とし穴として、`url.insteadOf` の `.git` suffix・`secrets` の `if:` 非対応・`inputs.default` 非評価が記録された (Issue #219)。

synvelis lane の実測（`f7aadd0` scratch clone）では、manifest 正規化→`CARGO_NET_GIT_FETCH_WITH_CLI=true` で `cargo fetch`→単一 SHA guard（15 crate が候補 SHA に単一解決・total=15・bad=0）→`mise run check` exit 0（10.66s）→`git lfs pull`+`mise run test` exit 0（23 suite・0 failed・`--locked` 整合）だった。audio-lens の scratch clone（987f236）では同一 sed 後に 14 dep の rev が候補へ置換され（features 保持・TOML 有効）、lock の 15 source 全てが候補 SHA に解決し、`cargo check --workspace --all-targets` が exit 0・25.78s だった。PR 分類検査スクリプト 5 case（未記入テンプレート・記入済み・unknown+解消先なし・unknown+解消先あり・セクション欠落）もローカル実行で全 pass と確認し、複数行 HTML コメントを記入と誤判定しないことも確認した (Issue #219)。

両 consumer の pin 遅れも実測された。audio-lens の現行 pin は ruviform main 比 12 commit 遅れ（gh api で manifest の `rev` を確認し `git rev-list --count` で計測）、synvelis は 5 member workspace で ruviform HEAD 比 39 commit 遅れ（git 追従 dep×10・ruviform-numeric/ruviform-ui 非含有）だった。関連追跡 Issue（synvelis #47/#48・audio-lens #131/#132/#127/#133・synvelis #28）は `gh issue view` で全て実在を確認した（#133 は CLOSED・他 OPEN）(Issue #219)。

証拠契約は候補 tuple の証拠（解決 SHA 捕捉・期待 SHA 照合・構造化 JSON artifact）として実装され、判定ロジックは `ci/consumer-verify/evidence.mjs` に単一権威として集約された（classify-ref/lane/finalize の 3 コマンド）。`shaMatch` は `EXPECTED_SHA`/`RESOLVED_SHA` から finalize 側で導出し（期待未提供=`null`、提供時に解決 SHA 未捕捉=`false`）、`GATE=run` 時のみ `RUVIFORM_REV` の 40-hex を要求する。blocked/not_run 終端経路では生値を「試行された入力」として記録し（`RUVIFORM_REV` 自身の不正形で finalize が throw すると証拠が消失するため）、env は allowlist のみ読み秘密系を転写しない。workflow は `actions/checkout`（ref 未指定 = dispatch 対象 ref）を preflight・両 verify job の先頭に配置し、script 導入前の候補 revision を検証する run でも証拠器が存在するようにした (Issue #294)。

実装上判明した障害と修復も記録されている。`runner` context は job env で使えず（actionlint が `jobs.<job>.env` での `${{ runner.temp }}` を拒否）、無条件先頭 step `Lane path env` が `$GITHUB_ENV` に `CONSUMER_DIR`/`LANES_FILE`/`EVIDENCE_FILE` を供給する方式とした。resolution step は `always() && gate==run` にした（clone step 自体の失敗時に GitHub が後続を skip するため、`always()` でなければ rev-parse 失敗を fail lane として記録できず証拠が欠落する）。証拠器は runner 同梱の `node` で実行する（`mise exec -- node` ではなく — gate=blocked/not_run 経路では mise install が走らず壊れ得る）。`unsupported` 固定行（実窓 host・macOS/実 OS lane）と `not_run` 固定行（未接続・Owner/再実行条件付き）の分離は review 指摘の修復として導入され、concurrency group の tuple 衝突は expected SHA + extra tasks を key に追加して解消した。SHA fetch の境界として、GitHub は unadvertised commit の fetch を受理するが GC 済み・未 push の SHA は clone step fail→`fail` 証拠として正直に出ること、`extra_tasks` は operator 信頼入力（pattern は shell 注入排除のみで意味論は制約しない）、job `timeout-minutes: 120` が暴走境界であることも記録された (Issue #294)。

証拠 schema は virtual-first Case schema v2 へ additive に拡張された。`SCHEMA_VERSION` を 1→2 に bump し、`CONTRACT = "consumer-verify-tuple/v1"`・`outcome` 語彙・`deriveStatus`/`coverage`/`markdownSummary`・top-level tuple/run/consumer 構造は不変を維持した。各 lane record は必須 `case_id`/`level`（`OS-L1`/`GUI-L2`/`EXT-L3`）/`environment_kind`（5 値閉集合）/`requirement`（`Required`/`Deferred`/`NotApplicable` — 結果軸と直交）を保持し、`readLanes` は `lane` コマンド経由でない行にも同一語彙の fail-closed 検証を課す（schema-v1 行・未知 enum・型不正・非 40-hex `resolved_ruviform_sha` を拒否）。`ci/daily/decide.mjs` は `kind`/`contract`/run/consumer/tuple/status のみ検証し `schemaVersion`・`lanes` を読まないため `contract` v1 固定で回復経路は不変で、`ci/tracker` の contract test は `deriveStatus`/`OUTCOMES` を import して `outcome` 名と 5 値語彙を pin した。記録経路は 3 系統（`rec()` spec 文字列・extra task の直接 `lane` 呼出・fallback `printf`）あり、全て同時更新しないと finalize が fail する構造を contract test で pin した。`rec()` は `"<case_id>|<level>|<environment_kind>|<requirement>[|<resolved_sha>[|<oracle>[|<fixture_version>]]"` の spec 文字列を第 1 引数に取り `local` + `IFS='|' read` で分解する方式で、field 6/7 省略時は flag を付与しない後方互換を維持し、job 内既定分類は `$DEF="OS-L1|deterministic-backend|Required"` で供給する。`resolved_ruviform_sha` は GUI candidate 行のみに限定した（run 全体は top-level tuple が既に束縛しており、candidate tree 評価との区別が意味を持つのはこの行のみのため）。Case 分類の確定マッピングは、既定 `OS-L1|deterministic-backend|Required`、GUI visual/OS + 実 window lanes が `GUI-L2|real-window|Required`（outcome `unsupported` 固定）、synvelis `PLUGIN-NATIVE-DOCK` が `EXT-L3|test-plugin|Required`（`unsupported` 固定）、macOS/実 OS lanes が `OS-L1|physical-device|Required`（`unsupported` 固定）とした (Issue #294)。

両 verify job の lane 集合は consumer の mise task 名に依存して構成された。verify-synvelis は presence check→fetch+lockfile guard→`check-ruviform-rev`→`check`→`test`（LFS pull）→`test-rt`→`check-headless-deps`→`sync-ui-deps`→`setup-ui`→`check-ui`→`test-ui`→`build-ui`→`check-ruviform-rev --require-vendor` の順で、manifest は build-ui の産物であるため vendor 検証は必ず後置される。verify-audiolens は fetch+lockfile guard→`check-ruviform-lock`→`check-ci`→`al-cli` ci build+`check-cli-headless`→`test-ci`（LFS pull）→UI 独立 chain（`sync-ui-deps`→`check-ruviform-rev --require-vendor`→`setup-ui`→`check-ui`→`test-ui`）の構成で、task の改名は lane fail または not_run として可視化される設計とした (Issue #294)。

GUI-CONTRACT lane は候補 tree を直接評価する step 群（`gui_candidate`/`gui_boundary`/`gui_semantic`）として両 verify job に追加され、Record step の固定 `not_run` 行を step outcome 由来の lane 行へ置き換えた。`gui_candidate` は `$RUNNER_TEMP/ruviform-candidate` へ `git init`+`fetch --depth 1 origin $RUVIFORM_REV`+`checkout --detach FETCH_HEAD` で候補 tree を取得し `rev-parse HEAD` を候補 SHA と照合し、候補 `mise.toml` の `[tasks.<name>]` 存在を grep probe して `boundary`/`contract` output を出力する（task 不在→owner 付き `not_run`、dispatch ref の代用は禁止）。候補に task がない旧 SHA で `not_run` ではなく `fail` になる混入を防ぐため、probe の grep 判定を record 分岐に pin し contract test で固定した。`gui_semantic` は rc 捕捉 + summary 追記 + exit の構造で、driver-lab の case 別 verdict JSONL を Job Summary に残しつつ、失敗時は元の exit code で step fail にする (Issue #294)。

## daily tuple 判定と contract v2

daily scheduler の検証単位は、単一 SHA から候補 tuple `(ruviform main SHA, audio-lens main SHA, synvelis main SHA, consumer-verify-tuple/v1)` へ一般化された（`ci/daily/decide.mjs` に `--mode tuple` 追加）。Actions run API は dispatch inputs を公開しないため、各 run が検証した tuple は `consumer-evidence-<consumer>-attempt-<run_attempt>` artifact の証拠 JSON から復元する fail-closed 経路を実装し、証拠なし・期限切れ・破損・内部不整合は全て `unverifiable`（verified にも無視にもせず、auto actor なら retry budget に保守的に計上）とする。`non-target`（証拠が完全に読めて tuple が candidate と異なる）と `unverifiable`（証拠が欠ける/壊れる）は区別される (Issue #294)。

artifact 処理には最小自前 zip reader を使う。依存追加を避けるため EOCD/central directory/local header を stdlib で走査し、data descriptor・zip64・method 0/8 以外は `ApiError`→unverifiable で、実運用の upload-artifact v4 zip（deflate）をカバーする fixture 側 deflate zip 生成テストを追加した。artifact zip DL は 302 `Location` を手動追従し token を署名 URL へ転送しない。consumer 一覧の正本は `candidate.consumers` で（config 側の `{name, repo}` は sha を持たず一致判定は解決済み sha を持つ candidate 側で行う — 初版は config 側を参照し全件 non-target になる bug を fixture テストで検出・修正）、`--consumer-repo` flag は env 既定を置換する（初回 flag 出現で env 由来リストをクリアし暗黙 union を防ぐ）(Issue #294)。

運用上の制約も記録されている。artifact 期限切れ（90 日）で verified tuple が unverifiable 化すれば再 dispatch する意図的 fail-closed で、evidence 走査上限超過は `evidence-truncated` hold、in-flight 全面抑制による最大 1 日遅延、`git ls-remote` の anonymous HTTPS 依存（private 化時は error outcome で可視化）がある。固定 `unsupported`/`not_run` 行を持つ consumer を含む covering run は verified にならず、全 consumer `status==="pass"` の成立は consumer 側 lane 実装に依存する（判定器のみが本側責務）。検証は `test-ci-daily` 111 pass・`test-ci-consumer-verify` 64 pass・actionlint 両 workflow pass・prek 全 hook pass・consumer repo への匿名 `ls-remote` で 40-hex SHA 返却を実測し、実 dispatch は fixture ベースの実装のため未実施で、merge 後の daily/手動 `workflow_dispatch`（`dry_run` 推奨）で初めて実測されると記録された (Issue #294)。

証拠 contract は v1→v2 へ一括 bump された。`evidence.mjs` の `CONTRACT`、`decide.mjs` 既定値+コメント、両 workflow の env/fallback/summary/ヘッダ、4 つの contract test、`docs/development-environment.md` を一括更新し、decide test に legacy v1→non-target の hard cutover pin と `resolveConfig` 既定 v2 pin を追加した。`schemaVersion`/`lanes` 未検査は維持する（consumer が必要とするのは tuple 同一性と status であり、証拠内部語彙は producer 側契約で contract 文字列が version 軸）。検証は `test-ci-consumer-verify` 84 pass・`test-ci-daily` 113 pass・`test-ci-tracker` 108 pass・actionlint 両 workflow pass・`node --test ci/` 354 pass で、`evidence.mjs finalize` の smoke で発行証拠 JSON の `contract`/`tuple.contract` が `consumer-verify-tuple/v2` であることを実測した。この変更で test-ci-consumer-verify が main 既存破損（consumer-side GUI contract 行の owner 注記更新に test regex が未追従）を検出し、base worktree で再現確認後に test regex のみ修復した（workflow lane 行は不変）(Issue #720)。

MSRV lane の初回 dispatch（run 43383950490、expected_sha=4a6026d8）では `test-observability-msrv` が `rolling_file_retention_*` 2 件で失敗し、`ci-summary` は msrv-verify:job-failure で fail-closed した（checkout-sha evidence は正常に提出・評価され、新 lane の evidence 契約は機能した）。原因は upstream `tracing-appender` 0.2.5 の `prune_old_logs` が `Metadata::created()`（birth time）で retention 対象をソートし、Linux runner で tight loop 連続 write の seed file が同一 timestamp tick を共有して削除順が readdir 順に退化したことだった。feature-gated test target は `--all-features` を使う MSRV lane でのみ実行されるため通常 lane では未検出で、MSRV lane の Linux 初走行で顕在化した。`SEED_FILE_BIRTH_GAP`（100ms）の実時間 sleep を seed 生成ループに挿入して修正し（birth time は明示設定不可のため実時間が唯一の lever）、2 回目 dispatch（run 43385858552）は run 全体 success・msrv-verify job success・ci-summary verdict PASS となった。retention fixture の 100ms sleep は filesystem timestamp 粒度への依存を残し（粒度 >100ms の FS では再発し得る）、upstream 恒久修正は別 Issue 候補と記録された (Issue #594)。

## Linux offscreen lane の実機検証

GT-05 の Linux Xvfb offscreen lane では、bare Xvfb では present が成立せず黒画面になるため openbox が必須要件、mesa 24.2 以上が必須（sw X11 WSI の `chain->depth` 修正が必要で、22.3.6 では depth-24 PutImage BadMatch で恒久黒画面）、`--test-threads=1` が必須（`_NET_WM_PID` は process 単位で一意で、occlusion 時に GetImage が下位 window を読めない）と確認された。window 解決は `_NET_WM_PID` + `_NET_CLIENT_LIST` 優先 + `QueryTree` fallback で、openbox は reparent するため root-child 列挙では拾えない。gpui 0.2.2 の `X11Window::window_handle()` が `unimplemented!()` で rwh seam が panic するため、capture 側は lazy に own toplevel を `_NET_WM_PID` sentinel（`usize::MAX`）で解決した。`client_geometry` の `GetGeometry` は inside size（border は drawable 外）なので `border_width` を引かない。`libc` の 0.2.189 pin は、xattr 0.2.3 が参照する `libc::ENOATTR` が libc 0.2.190 で Linux cfg から削除され gpui の Linux build が不能になった upstream 既知問題への lockfile 修正だった (Issue #314)。

実機検証は Docker Debian + mesa 25.0.7 + Xvfb + openbox + lavapipe で行い、`cargo test -p ruviform-ui-gpui --features real-scenario --test real_window -- --test-threads=1` が 2 tests pass（約 96s）した。lane と同一形状（xvfb-run + sh -c + openbox + `_NET_SUPPORTING_WM_CHECK` probe + `--test-threads=1`）で再現し、bare Xvfb 対照実験では同一 build が黒画面となり openbox/mesa の寄与を分離した。xtrace では lavapipe present が window drawable への PutImage（depth-24 vs window depth-32）で BadMatch を観測し、mesa 24.2.8 source で `chain->depth` 使用を確認した。Windows 側の test-ui-gpui/check-ui-gpui/lint-ui-gpui/test-ui-consumer-observation/test-ui-scenario-contract-gpui 等は全 pass、Linux の `cargo check`/`clippy -D warnings`（gpui feature）は Docker で pass した。ubuntu-24.04 stock mesa（24.2.x）による初回実測は PR CI で確認予定とし、source 上 `chain->depth` 修正済みだが実機未検証と記録された (Issue #314)。

## CI 照合と証拠の SHA 固有性

CI 照合は SHA 固有で行い、祖先 SHA の成功を HEAD の Pass に転用しない原則が確立された。この原則は docs-only の 5 文書チェーン（spec→design→test-spec→plan→task）を通じて Issue 受入を正本化する枠組みの一部として設計され、判定語彙 `Pass`/`Fail`/`Unsupported`/`NotRun`/`Blocked` と「`NotRun` を `Pass` にしない」正直性ルールとともに capability matrix・形式比較・Owner 境界・AC 写像へ集約された (Issue #127)。

既存 Ubuntu CI（ci.yml/daily-ci.yml/consumer-verify.yml）の lane 定義と main 上の成功 run を gh で照合し、対象 SHA・run URL・job・結果・テスト集計を台帳化した。run 43439434737（@ `365c74ac`）の全 lane 成功・テスト集計・checkout-sha artifact を SHA 単位で確認し、`365c74ac..621490e8` に `crates/`・`mise.toml`・`ci.yml` 差分があるため HEAD（`621490e8`）は `NotRun(Pending)` とした。照合手法は `gh run list/view`・`gh api .../artifacts`・`gh run view --job --log` の 4 段照合である。macOS/Linux L1（必須）では Native Build/Link・必要 Feature・Headless/RT の既存 CI を同候補 SHA（365c74ac）で確認した。Ruviform 共通 runtime 最低要件・distro/配布方式の採否/未確証・packaging の Owner 境界は文書上確定されたが、実 deb/AppImage/Flatpak の作成・署名は主張していない。4 種の監査スクリプトで blocking finding なし、`mise run fmt-check` exit 0 だった (Issue #127)。

## 記録の範囲と限界

以下の検証は記録上 NotRun または deferred として扱われ、実施済みの Pass には含めない。

consumer-verify の実 runner dispatch は複数 slice で NotRun と記録された。証拠 contract v2 の実走 artifact 確認・consumer oracle lanes・GUI-CONTRACT lane の実 `workflow_dispatch` 再実行・daily tuple 判定の実 dispatch は、全て post-merge の Coordinator 管轄で未実施とされ、fixture ベースの実装に対する実 GitHub API での tuple 判定・dispatch は merge 後の daily/手動 `workflow_dispatch`（`dry_run` 推奨）で初めて実測される。実 daily dispatch の実走証跡（run API 制限・ops 事項）・reconcile の consumer-verify scope の実データ処理（次回 scheduled/manual 実行で初めて処理）・both-consumer-pass の実測（audio-lens 側 export portability 修正待ち）・`CROSS_REPO_DEPLOY_KEY` 等 credential 設定（人手の作業）も NotRun とされた。GUI-VISUAL/OS lanes・`PLUGIN-NATIVE-DOCK`・macOS/実 OS lanes は実機 gate の固定 `unsupported`/`not_run` 行で、各 Owner 側の実装待ちである (Issue #294, Issue #219)。

schema/記録層の制約も記録されている。`requirement` は現行 lane 全て `Required` で `Deferred`/`NotApplicable` の実使用例はなく、optional 項目（oracle/fixture_version/expected/observed/device/endpoint/plugin/abi/sdk/arch/os_ver）は schema が受理するが workflow は `resolved_ruviform_sha`（GUI candidate 行）以外を未記録である。consumer test は機械可読 verdict を出力しないため per-case（per-test fn）粒度の lane 行はなく、per-case JSONL emitter + ingest 契約は consumer repo 側後続 slice、`fixture_version` は crate version+SHA で fixture 内部の scenario/seed 版は識別しない。oracle lane は deterministic-backend の headless 検証であり、実 OS・実機・GUI・native plugin の証拠ではない。`docs/development-environment.md` の証拠契約記述は別 Worker リースのため未同期とされた (Issue #294)。

その他の NotRun・deferred 項目は次のとおりである。Issue #2 の V-8（CI ディスク計測の実ディスパッチ）は default branch マージ後として区別記録。Issue #19 の AVX-512・aarch64 NEON は未計測（Issue #55 送り）。Issue #328 の AC3（同一 PR 連続 push での旧 run cancel 実測）と非 cancel 実測は coordinator 引き継ぎ。Issue #329 の Cargo.lock 更新時・toolchain 更新時・fork PR の GHAC 挙動・RT/ICC/L1/bench への展開・consumer 側適用（audio-lens #148/synvelis #147）は NotRun/範囲外。Issue #330 の CI 3 OS matrix 実測は PR CI run での確認事項（ローカル検証は Windows のみ）。Issue #332 の Playwright version bump 時の cold 再計測は key 自動切替のため不要と設計判断したが、実際の bump PR での観測は未発生。Issue #333 の部分集合 expected の実 run 証拠と workflow_dispatch・base retarget・kill switch の実動作観測は Shadow 期の確認対象として未観測。Issue #346 の After メトリクスは merge 後の選択実行 run で収集予定。Issue #367/#368 の実 cron・実 workflow_run 発火・実 Issue・実 dispatch は全て未検証（offline contract test + actionlint のみ）で merge 後の初回実測が受入。Issue #411 の macOS/Linux 実機は NotRun（Windows 11 x64 のみ実測）で、consumer 側 lock 更新と `test-msrv` は別作業と切り分け。Issue #650 の `*-msrv`・`*-full`・3 OS 横断は明示対象外（Daily Full CI 委譲）。Issue #720 の AC5（post-merge 実 run gate）は Coordinator 所有の post-merge dispatch で追跡。Issue #127 の現行 main HEAD（`621490e8`）の CI 結果は未取得（daily-ci dispatch 待ち・NotRun(Pending)）で、実 deb/AppImage/Flatpak の作成・署名は行っていない (Issue #2, Issue #19, Issue #127, Issue #328, Issue #329, Issue #330, Issue #332, Issue #333, Issue #346, Issue #367, Issue #368, Issue #411, Issue #650, Issue #720)。

既知の残存リスク・限定として、Issue #314 の ubuntu-24.04 stock mesa（24.2.x）での実機実測は PR CI での確認予定（source 上修正済みだが実機未検証）で、bare Xvfb で present が成立しない正確な機序（gpui 側の visibility/refresh 起因か mesa WSI の present mode 起因か）は未解明。Issue #329 の cold write error 対策（GHAC rate limit/並列書込競合の恒久対応）は follow-up として残った。Issue #331 の step 時間短縮は run 間変動（16–92s）が大きく、単発差分を恒常的改善と断定するには継続計測が必要。Issue #594 の retention fixture は filesystem timestamp 粒度への依存を残す。Issue #598 の `docs/development-environment.md` lane 構成記述の更新と `POLICIES.md` の行末空白修復は編集範囲外として未対応。Issue #294 は umbrella のため各 slice 完了後も Open 継続（PR は `Refs #294` のみ）と記録された (Issue #294, Issue #314, Issue #329, Issue #331, Issue #594, Issue #598)。

この記録は所定の文書集合の内容を対象としており、リポジトリ全体の網羅的な再調査ではない。workflow ファイルや `ci/` 配下スクリプトの実装そのものとの逐語照合は行われておらず、各 CI run の結果は文書スナップショット時点のもので、GitHub Actions 上の最新状態は本記録では再確認していない。一部の作業単位（Full CI 化・dispatch 専用化の実装記録、dispatch overhead 計測の後続分析レポート等）では対応する記録文書が見つからず、検証詳細は各タスク側の記述に依存している。また Issue #294 は umbrella であり、各 slice の完了後も Done 基準（初回両 Consumer CI 実走・追従更新・起票〜解消ループ）を満たしたかは記録からは判断できず、Open 継続とされた。
