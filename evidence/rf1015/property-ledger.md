# rf1015 Property ledger — wire / archive / structured documents / WAV

本 ledger は Issue `scarecrow173/ruviform#1015` slice 1 の assurance pack である。rf#806 の harness inventory をなぞるのではなく、製品契約と risk がまとまる Property group を単位に、73 個の proptest と 20 個の Kani proof を再編する。製品コード、proof harness、mise lane はこの slice では変更しない。したがって「新検証」列は実施済みの結果ではなく、後続実装 slice が実行する設計である。

正本の関係は次のとおり。`POLICIES.md` §6 が方法論、`docs/specs/formal-verification.md` が rf#806 当時の契約・Bound・未証明領域の inventory、`evidence/rf806/` が旧実行証跡、本書が Property 起点の再設計台帳、`evidence/rf1015/verification.md` が slice 1 の作業証跡である。

## 1. 独立軸と判定語彙

要求状態、verdict、保証種別、対象、同期状態、失敗原因は独立した軸として扱う。CI green、プロセスの exit 0、Timeout、OOM、環境欠如、proof 未発行を Proof Pass に転用しない。

| 軸 | 値 | 意味 |
| --- | --- | --- |
| requirement state | `Required` / `Deferred` / `NotApplicable` | 現行受入で必要か、条件成立まで保留か、対象外か。slice 1 は設計のみなので、後続実装で必要なものを `Required`、現行維持で足りるものを `Deferred`、proof 対象から外すものを `NotApplicable` と記す。 |
| verdict / result | `Pass` / `Fail` / `NotRun` / `Unsupported` | 実行結果。Timeout・OOM・環境欠如は `NotRun` と原因付きで記録し、proof の反例だけを `Fail` と区別する。 |
| assurance kind | `Example Tested` / `Property Tested` / `Bounded Exhaustive` / `Contract Composed` / `Integration Tested` / `Not Assured` | 保証の強さと種類。proptest を形式的証明と同じ扱いにしない。 |
| target | `implementation` / `model` / `abstraction` / `test double` | 何を検査したか。KaniSink や独立 oracle を実装そのものと混同しない。 |
| sync state | `synced` / `design_only` / `not_synced` / `deferred` | 製品・仕様・skill・mise・証跡の対応状態。mise の選択再実行入口は未実装なので `not_synced` と記す。 |
| failure cause | `Product Defect` / `Model Error` / `Resource Limit` / `Environment` / `Oracle Mismatch` / `None` | 失敗または NotRun の原因分類。環境起因を製品欠陥と混同しない。 |

## 2. coverage の数え方

2026-11-26 に `#[test] fn` と `#[kani::proof]` を対象ファイルへ照合した結果、proptest は `formal_ipc` 7・`formal_transport` 4・`formal_archive` 18・`formal_structured` 35・`formal_wav` 9 の計 73、Kani proof は wire 5・archive 3・structured 3・WAV 9 の計 20 だった。counting 手順とコマンドは `evidence/rf1015/verification.md` に記録する。

下表の `既存資産` は proptest を `pt:`、Kani proofを `kp:` で示す。1 つの proof が複数 group の証拠になる場合は、主たる group にのみ counting 上の所有を置き、他 group では `(共有)` と記す。これは重複した保証を足し算しないためである。

各 group の欄は次の既定を持つ。特記のない限り `kani::assume`、Stub、test double、feature gate はなく、failure cause は `None`、proptest の実行コストは `test-formal` shared lane（rf1015 baseline では 5 suite 合計 8 秒未満の incremental run）として記録し、証跡は `evidence/rf1015/verification.md` とする。Kani のコストは rf806 envelope を旧 baseline として行へ記す。状態領域は行の subject に書く stream/cursor/receipt 状態であり、単発入力だけの groupは stateless と読む。assume の充足可能性と必要経路の到達性は §5 の手順で監査し、通常の concrete/symbolic生成で到達できる行には個別注記を置かない。到達不能性、test double、入力域除外、保証縮小がある行だけ、該当欄または §5 の audit example に明示する。

## 5. 健全性 audit と保証差の判定手順

各 groupについて、次の順で監査する。

1. 契約参照が製品 rustdoc、公開仕様、consumer-visible behaviorのどれかを特定する。oracleだけに根拠がある場合は `oracle_mismatch`候補とする。
2. assume、Bound、Stub、test double、cfg/feature gateを列挙し、充足可能な入力が存在するか、必要経路へ到達するかを確認する。
3. 旧保証と新保証を assurance kind・target・入力域で比較する。狭くなった軸は「保証差」に明示し、別の検証で補うまで `synced`にしない。
4. 除外領域が必要経路を含まないかを確認する。含む場合は requirement stateを下げず、未証明領域として `Required`のまま残す。
5. mutationまたはfault injectionで、意図した契約違反が検出されることを確認する。検出されなかった場合は boundary densityまたは oracle不足として記録する。
